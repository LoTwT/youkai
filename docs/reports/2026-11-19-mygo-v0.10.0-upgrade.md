## 安装适配与模板证据

`tools/mygobuild` 仍绑定原来的 6 个上游文件；其中 `nsis.go`、`installps1.go`、`checksums.go`、`publish.go` 与 v0.9.0 字节相同，只有 `build.go` 与 `updates.go` 更新 pin。`build.go` 的差异是帮助文本、手机平台分支和 Linux desktop exec，不经过 Windows 安装器模板；`updates.go` 的差异是更新下载重试与 `updates.url` 校验，不经过安装器模板。NSIS 3.13 的版本、镜像与压缩包 SHA-256 也未变。

用 v0.10.0 实际运行生产入口 `go run ./tools/mygobuild` 生成 Windows 安装包，并保留输入/输出模板：

- `installer-upstream.nsi` SHA-256 `9de87b27a3d5390b01c10f8cdadc1eca6721b6a6fb2fce2cb11714b0be63d69b`。
- 与冻结 fixture `tools/mygobuild/testdata/upstream.nsi` 逐段比较，差异只有 BOM、`OutFile`、`MUI_ICON`/`MUI_UNICON`、sentinel include 路径与 `File` 行；两个完整 `CloseApp`、Section 结构、注册表/卸载/快捷方式/协议动作完全一致。
- 转换后 `installer-adapted.nsi` SHA-256 `f51cb42a3665a1e427d44bf8872ff39c16bdf69f66b130610f8be9b35e3beae1`，含两个 `nsExec::ExecToStack /TIMEOUT=15000`，前置检查位于普通 `File` 与 `RMDir /r "$INSTDIR"` 之前，无 `Stop-Process`、`CloseMainWindow` 或旧 PS1 独立强杀辅助函数。

### test-v 渠道用法注释（首轮复审 Required 1）

首轮复审用 `updates.tagPrefix=test-v` 实跑生产入口，`install.ps1` 完整摘要不匹配并 exit 1；`v` 与未设置前缀时通过。逐行比较 pinned v0.10.0 生成器与真实脚本确认：仅当渠道为 `test-v` 时，上游除改写 `$releases`、`$api`、`$tagPrefix`、`$assetsApi` 外，还把头部 `#   irm … | iex` 注释从 `releases/latest/download/install.ps1` 改为 `releases/download/test-v<version>/install.ps1`。旧归一化只覆盖四个赋值，漏掉联动注释，因此该缺陷在 v0.9.0 基线同样存在。

修复仍保留完整模板验证：

- `normalizePS1` 现在要求项目版本为 `major.minor.patch`，并要求 `updates.tagPrefix` 为 `""`/`v`（上游都映射到未标记的 latest 源）或 `test-v`；其他前缀直接拒绝。
- 对 `test-v`，校验头部注释、`$releases`、`$api`、`$tagPrefix`、`$assetsApi` 与 `$github = $true` 全部是 pinned 生成器的精确形式，再把合法 test 注释归一化到已绑定的 stable 形式。`ps1TemplateSHA`、`nsisTemplateSHA`、关闭/运行拒绝、退出传播、签名、manifest-last 与最终摘要逻辑均未改。
- 错误/重复/移位注释、版本不符、来源变量漂移、`$github = $false` 或未知前缀均拒绝。`TestPS1FullControlAndFailure` 覆盖 stable、`v`、`test-v` 三种可接受形式及以上拒绝路径；旧的“只替换 `tagPrefix`”现在必须被拒绝。

隔离临时副本按 workflow 写法只改 `mygo.json` 的 `updates.tagPrefix`，用同一 v0.10.0 生产入口实跑两渠道；两处均 exit 0，生成并转换完整模板、通过最终 `SHA256SUMS` 校验。
