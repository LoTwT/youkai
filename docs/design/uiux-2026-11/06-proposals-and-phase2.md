### 1.1 首版范围调整（2026-11-03 用户决定）

- **首版只支持 Windows 本地客户端。** Windows 云客户端和 mac 云客户端移出首版。权威范围已在[架构 §6“平台与客户端”](../../specs/scanner-architecture.md#6-首版功能范围)按此修改。
- **mac 仍是开发平台。** [04](04-journeys-mac.md) 的 mac 旅程保留为“后续版本参考”，不进入首版优先级；P-08 随之移出首版。
- 其他规格中与新范围冲突的地方（架构 §6/§7 其余条目、T1、T2、T5、T7、实施清单、`release.md`、`docs/index.md` 与决策记录等）不在本 PR 修改；用户已确认这些修改另开一个范围 PR 处理（2026-11-03），mac DMG 是否一起移出在该 PR 中决定。

### 1.2 其他产品决定（2026-11-03）

- **装备者警告暂不处理。** 例如 11-02 真机扫描中 108 件已装备盘的 `agentId` 为 null（[真机报告](../../reports/2026-11-02-windows-local-field-acceptance.md)第 131 行）。用户接受留空直接导出；W3 不增加批量处理警告的流程。状态矩阵仍要按判定顺序区分“待补录 / 待校对 / 有警告但可导出 / 已通过（无 warning）”四类（[05 S7](05-state-matrix.md#s7-校对w3)），避免第二阶段把警告件当成待校对件。
- **导出只提供通用文件。** 不针对特定工具适配，也不承诺特定工具兼容；W4 写明 JSON 与 CSV 的选择依据。
- **使用频率未知。** 用户认为无法假设扫描、校对、导出的频率。设计不能依赖频率假设：首次进入和回访两条路径都要高效，首屏不能只为其中一种优化。
- **不做件级跨扫描对比。** 规格没有跨会话的物品身份（[JSON/CSV v2](../../specs/scan-json-format.md#标识与目录子集)：只用 `session.id + items[].sequence` 标识一次观测，禁止用属性哈希充当物品身份），因此不设计“新增 / 删除 / 修改”的单件对比视图。记录级的对比（日期、件数、覆盖并排）由历史列表承担。

## 3. 给第二阶段的输入

第二阶段负责布局、导航结构和视觉。以下是本阶段得出的、第二阶段必须回应的要点（不是布局方案）。首版只覆盖 Windows 本地客户端（第 1.1 节）。

1. **明确的设计假设：扫描中完全没有反馈。** 扫描时游戏在前台，youkai 窗口在游戏后面，看一眼主窗口或点托盘都可能停止扫描（C-01、C-03）。第二阶段按“扫描期间用户收不到任何 youkai 反馈”设计；**结束通知（P-06）是唯一的反馈渠道**。托盘或菜单栏的状态显示等 P-02 实测通过后再加入。主窗口的扫描相关内容服务于“开始前”和“结束后”。
2. **主干从回访开始，首次使用是汇入支线。** 主干为：回访 → 准备检查 → 扫描 → 结果摘要 →（有待校对项或用户主动检查时）校对 → 导出；首次使用是汇入准备检查的支线（[03 旅程一览](03-journeys-windows.md#旅程一览)）。使用频率未知（第 1.2 节），首次与回访两条路径都要高效。
3. **准备检查是开始前的唯一入口**（P-03）：每项显示“当前值 → 需要值”，包含权限与提权引导（P-05）、停止热键、30 秒规则与倒计时（P-04）、预计耗时（P-14）。首次显示解释，回访显示精简状态，失败时回到同一份清单。
4. **每种失败都要有“原因 + 怎么做 + 下一步入口”。** 05 的 S3、S6 列出了全部失败状态；故障码与英文报错只能放在诊断信息里（C-29、D-04），并能复制或打开诊断目录（P-15）。部分覆盖的结论页要为将来的“只重扫不完整位置”（P-12）预留入口的位置，但首版不实现。
5. **校对是 P0 能力，不是每次都走的步骤。** 11-02 真机全量扫描 1,017 件中只有 1 件待校对，另有 108 件装备者未识别、21 件装备状态未判定，均只带 warning、可直接导出（[真机报告](../../reports/2026-11-02-windows-local-field-acceptance.md)第 62 行、第 131 行）。单次数据不能定稿，但足以否定“校对是最高频旅程”的判断。需要校对时：证据与表单同时可见、字段能对应证据、“确认并下一项”能全程用键盘完成（P-11 第②层）；结果按判定顺序分为“待补录 / 待校对 / 有警告但可导出 / 已通过（无 warning）”四类（[README 术语](README.md#术语)）；待补录的件也在校对视图里补录；警告件不进入校对流程（第 1.2 节）。
6. **导出前要有摘要**：纳入、排除（及去校对的入口）、覆盖结论、不含截图、写入位置；成功后给出打开目录的入口（W4、S8、D-11）。格式选择依据：JSON 带来源会话、覆盖结论、筛选方式、排除数量和目录子集；CSV 是面向表格的一行一件单表，不含这些信息（[JSON/CSV v2 §5](../../specs/scan-json-format.md#5-csv-导出)）。只提供通用文件（第 1.2 节）。
7. **平台写法集中在一处**：快捷键写法、托盘点击语义、托盘图标位置（C-04、C-13）。扫描中所有恢复入口都要写明“停止扫描并打开”（T1 §2）。
8. **优先级不等于显著性**（[03 写法说明](03-journeys-windows.md#写法说明)）：W3 是 P0 能力但不必占每次的主路径；W6 是 P2，但磁盘不足阻止开始时必须是主流程的出口。
9. **低频功能不挤占主流程**：更新、关窗偏好、快捷键（W7）；清理见上一条。
10. **核对 MyGo 能力后再定方案**：表格弹性列、图片缩放与平移、日期选择、界面语言固定为中文、系统通知与托盘气泡（P-06）、托盘菜单的动态文字（P-02）。
11. **可访问性的最低要求**：关键旅程（准备检查、W3、W4、W8）可全程键盘完成；状态不只靠颜色表达。
12. **每一屏的信息层级**（不是布局，第二阶段可改；“首要问题”是该屏必须一眼回答的问题）：

    | 屏 | 首要问题 | 主操作 | 次要信息 | 按需展开的详情 | 空状态 | 失败出口 |
    | --- | --- | --- | --- | --- | --- | --- |
    | 准备检查 | 现在能不能开始？ | 开始扫描（条件全部满足时） | 停止热键、30 秒规则、预计耗时、目标客户端 | 每项的“当前值 → 需要值”与调整方法；权限的提权引导 | 找不到游戏：说明需要先启动游戏并打开仓库页 | 每个不满足项给出调整方法；磁盘不足直接进入清理（W6） |
    | 结果摘要 | 这次扫全了吗、能直接导出吗？ | 导出（有可导出件时）；有待校对项时“去校对” | 待校对数、有警告件数、可导出数（截图默认保留，结束时不询问，P-13） | 不完整位置及原因、计数明细、终止原因与阶段、诊断（P-15） | 0 件采集：说明原因并回到准备检查 | 故障结束：原因 + 怎么做 + 重新开始；保存失败：重试（升为首要） |
    | 校对 | 这件哪里要改、证据是什么？ | 确认并下一项 | 剩余待校对数、当前件的问题字段 | 原始文字、修订前后值、全部字段 | 待校对为空：显示完成并引导导出 | 校验失败：字段旁说明；保存失败：留在当前件并重试（升为首要） |
    | 历史 | 我要找的记录在哪？ | 打开记录 | 日期、客户端、件数、覆盖、待校对与可导出数 | 占用、导出与删除操作 | 没有记录：引导开始第一次扫描 | 记录损坏或不可读：说明原因并允许删除 |
    | 导出 | 导出了什么、写到哪里？ | 导出 JSON / 导出 CSV | 纳入数、排除数、覆盖结论、“不含截图”、写入位置 | 格式区别、排除原因明细 | 0 件可导出：说明原因，默认引导去处理排除原因 | 写入失败：原因与重试；内部记录不受影响 |

    保存状态只在失败或进行中时需要用户注意；成功时弱化，失败时升为该屏的首要问题（C-25）。
13. **核心对象与入口**：

    | 对象 | 说明 | 与其他对象的关系 |
    | --- | --- | --- |
    | 活动扫描 | 准备 → 采集 → 收尾中的一次会话；同一时间至多一个（C-22） | 收尾保存后成为一条已保存记录 |
    | 已保存记录 | 一次扫描在本机保存的结果，可从历史重新打开（F-25） | 包含多件；可多次导出；P-12 将来可能让一条记录由多次会话组成 |
    | 单件 | 一件驱动盘的一次观测，以会话 + 序号标识；没有跨记录身份（第 1.2 节） | 属于一条记录；校对只修改记录，不操作游戏 |
    | 导出文件 | 从记录的一个已保存修订生成的 JSON 或 CSV，写入下载目录 | 独立于记录，清理不删除它（C-27） |

    | 场景 | 进入点 |
    | --- | --- |
    | 首次使用 | 首次启动 → 准备检查（W1） |
    | 回访 | 启动 → 最近一条记录的状态与“再扫一次”同时可达（W5a、W2-R） |
    | 再扫 | 准备检查 → 新会话 → 新记录，不覆盖旧记录（W2-R） |
    | 继续校对 | 最近记录或历史 → 记录 → 待校对项（W5a 或 W5b、W3） |
    | 再导出 | 最近记录或历史 → 记录 → 导出（W5a 或 W5b、W4） |
14. **窗口的硬边界**：默认与最小窗口尺寸由第二阶段决定（现状评审发现默认宽度只比分栏断点少 4 px，见现状 H3）；**单显示器下 youkai 窗口无法与 1920×1080 的游戏窗口并排**，用户是读完准备检查再切到游戏，不是对照着调整；必须在 125% 缩放下成立（现有 Windows 实测均为 4K + 125%，[T2 §3.2](../../specs/t2-platform-capture-input.md#32-可验收的窄显示配置候选)）。
15. **点开始后 youkai 留在原地**（P-09 不采纳）：游戏切到前台后会盖住 youkai，倒计时与准备状态只在用户切回之前可见；设计不能依赖扫描中可见的 youkai 窗口。
16. **待定：保存失败重试时的通知频率。** 按现在的流程，每次重试保存失败都会再发一条通知（F-37、03 W2 流程图），而用户此时可能已在 youkai 窗口里手动重试。第二阶段决定：只在第一次失败时通知，还是只在 youkai 窗口不在前台时通知。
17. **实现结构问题**（现状 S1–S4）不在设计范围，但第二阶段的布局若要求新的状态（预检明细、位置进度、诊断详情），需要同时列出对服务层快照的要求（P-03、P-04）。
18. **导航结构不以现有规格为约束**（P-11 第①层）：T6 第 5 行“布局以 `internal/ui` 为准”在第二阶段开始前作废，三个并列目的地、侧栏宽度、扫描与校对的从属关系、历史行内操作和列显隐都需要由旅程重新证明；第②、③层的功能要求与数据契约保留。05 的“下一步”列只写目的状态，不写导航方式。
