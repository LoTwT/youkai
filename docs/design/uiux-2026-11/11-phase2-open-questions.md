# 11 第二阶段待用户决定的问题

**第二阶段草案**（2026-11-03）。以下 6 个问题会改变布局或规则，需要用户在检查点 2 决定；每条给出推荐选项。编号与主控发给用户的问题一致；原定“不超过 5 条”的限制经主控批准放宽为 6 条。正文中凡是按推荐写入的地方都注明了题号，待用户确认。其余常规选择已在 07–10 中按推荐值写入，用户不同意时可直接指出。

## Q-01 导航结构

| 选项 | 说明 |
| --- | --- |
| **A. 窄导航轨 + 以记录为中心的工作区（推荐）** | 首页 / 记录 / 设置三个目的地；结果摘要、逐件校对、导出都挂在一条记录下；首页同时放准备检查和最近记录（[07 §3](07-information-architecture.md#3-导航模型)）。 |
| B. 保留现有宽侧栏结构 | 扫描 / 历史 / 设置三个目的地，扫描与校对是“扫描”的两个阶段；从历史重开的记录在另一个目的地。 |

推荐 A：回访的三个选择（再扫、继续校对、再导出）在首页同时可达（W5a），校对拿回侧栏占用的宽度（现状 H3），刚扫完和从历史重开走同一套视图。

## Q-02 默认与最小窗口尺寸

| 选项 | 说明 |
| --- | --- |
| **A. 默认 1180 × 760，最小 960 × 640 DIP（推荐）** | 1080p + 125% 放得下；4K + 125% 可与游戏并排；最小宽度下截图与表单仍并排（[09 §1](09-window-and-interaction.md#1-窗口硬边界)）。 |
| B. 沿用现状默认 1020 × 700，最小 860 × 560 | 窗口更小，但默认宽度下校对的列表要收起，最小宽度下截图与表单无法并排，需要放宽 P-11 第②层。 |

## Q-03 首次隐藏提示的形式

| 选项 | 说明 |
| --- | --- |
| **A. 第一次点 × 时先弹对话框说明图标位置，确认后再隐藏（推荐）** | 一定能被看到；之后可在设置 › 常规重看（P-10）。代价是第一次关窗多点一下。08 §9 已按此写入，待本题确认。 |
| B. 直接隐藏，同时发一条托盘通知说明位置 | 不打断，但 MyGo 在 Windows 上的通知就是托盘气泡（[09 §4.7](09-window-and-interaction.md#47-结束通知)），可能被系统屏蔽或错过；托盘不可用时根本发不出去（[09 §4.9](09-window-and-interaction.md#49-实测清单) T-07）。 |

## Q-04 保存失败的通知频率（06 §3 第 16 条）

| 选项 | 说明 |
| --- | --- |
| **A. 每次收尾只在第一次保存失败时通知一次（推荐）** | 重试是用户在窗口里发起的，用户此时就在看 youkai，结果只在窗口内显示（[09 §4.8](09-window-and-interaction.md#48-06-3-待定项的建议值)）。错过的通知能否在 Windows 通知中心找回尚未实测（[09 §4.9](09-window-and-interaction.md#49-实测清单) T-01），所以首页会一直显示保存失败状态，不依赖通知。 |
| B. 只在 youkai 窗口不在前台时通知，每次失败都可能通知 | 需要可靠判断窗口是否在前台；手动重试时用户通常就在窗口里，实际效果接近 A，但规则更难测试。 |

## Q-05 首页的主按钮

| 选项 | 说明 |
| --- | --- |
| **A. 始终是“开始扫描”；最近记录卡的“继续校对（n 件）”是次要按钮（推荐）** | 首页的位置和主操作稳定；使用频率未知，不为某一种回访意图优化（[06 §1.2](06-proposals-and-phase2.md#12-其他产品决定2026-11-03)）。 |
| B. 最近记录有待处理件时，“继续校对”升为主按钮，“开始扫描”降为次要 | 对“扫完还没校对完”的回访者少一步思考，但同一屏的主按钮会随数据变化，且可能诱导用户先校对一条已经过时的记录。 |

## Q-06 是否采集详情面板图

校对屏原设想的“上下文截图”在现有证据里不存在：每件只保存文字行裁剪和稀有度徽标、装备者头像等少量裁剪（[10 R-07a](10-service-requirements.md#r-07a-行裁剪与表单字段的对应)）。补采面板图要改采集与存储，属于用户决定。

| 选项 | 说明 |
| --- | --- |
| **A. 首版不采集；校对屏只显示逐行裁剪列表，点选字段时高亮对应的那一行（推荐）** | 不改采集与存储；“字段能对应到证据”靠行角色到字段的映射实现（R-07a，P0）。代价是看不到整块面板的排版，例如副词条的上下位置只能从行的顺序判断。**选 A 即修正第一阶段 F-18 与 05 S7“查看一件”中的“上下文截图”**（[08 §3.1](08-screens.md#31-三个区域)），T1 §1 的同步留到第二阶段定稿后。 |
| B. 每件额外保存一张详情面板图 | 校对时能看到完整面板并框出字段。按像素推算，每件文字证据占用至少变为现在的约 3.9 倍，截图默认永久保留，增量一直累积（[10 R-07b](10-service-requirements.md#r-07b-采集并保存详情面板图)）；需要同步架构 §5 与 T5 §6。 |
| C. 只为待处理件保存面板图 | 存储增量很小，但识别结果在采集之后才知道，需要先暂存每件的面板图、收尾时再删掉不需要的，采集与收尾都更复杂。 |

推荐 A：校对是 P0 能力但很少走（11-02 真机 1,017 件只有 1 件待校对，[06 §3 第 5 条](06-proposals-and-phase2.md#3-给第二阶段的输入)），行裁剪本身就是识别所用的原图，足以对照文字；为少数件把全部扫描的证据占用放大至少约 3.9 倍不划算。实测发现行裁剪不够用时，再按 B 或 C 补。
