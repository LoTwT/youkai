# 10 对服务层和契约的需求

**第二阶段草案**（2026-11-03）。列出 07–09 的设计需要、但当前服务层快照或契约没有提供的数据和能力，作为第三阶段拆分实施的输入。这里只写“需要什么、给谁用、出处”，不设计接口；接口与规格修改在第三阶段按单一事实来源落到架构、T2、T6 或 JSON/CSV 规格中。

“现状”一列基于 `main` 的 `5a78e10` 阅读代码：服务快照为 `internal/app/service.go:483-506` 的 `Snapshot`（会话 ID、修订号、`Busy`、`SavedCount`、`SavePending`、`SaveError` 和内核快照），内核快照为 `internal/scan/types.go:234-251`（阶段、结束类型、`InputPermitted`、首个触发、故障、计数）；记录列表为 `internal/record/store.go:207-229` 的 `RecordInfo`（ID、最新修订、保存时间、占用、截图占用）。

## R-01 只读准备检查

需要一个不建立会话、不占用扫描占用、不发送输入的检查入口，返回每个检查项的：项目、结论（满足 / 不满足 / 无法判断 / 点开始后检查）、当前值、需要值、故障码、检查时间。项目至少包括 [08 §1.1](08-screens.md#11-准备检查清单) 的目标客户端（含候选列表）、权限（完整性级别）、档位、工作区、DPI、停止热键可注册、磁盘空间（含需要的最小空间）、识别资源是否完整（只核对文件，不加载模型，F-05）。

- 点开始后仍按规格完整预检，旧结果不能当作通过（P-03 代价列）。
- 停止热键“可注册”只能通过试注册再释放得到；需要确认这不会和“仅扫描期间注册”的规定冲突（[T2 §2.2](../../specs/t2-platform-capture-input.md#22-macosscreencapturekit-窗口流与-quartz-输入)）。
- 规格落点：架构 §5 需要定义这个只读检查（P-03 代价列已指出）。

## R-02 准备阶段的截止时间与激活结果

快照需要给出准备阶段的截止时刻（或剩余时间）以及“请求激活游戏”的结果（已切到前台 / 被系统拒绝）。现有实现已在日志里记录 `accepted after N ms` 与 `not foreground after 500 ms`（[T2 §2.1 Windows 端口接入](../../specs/t2-platform-capture-input.md#21-windowsgdi-客户区裁剪与-sendinput)），但没有进入快照。

## R-03 准备阶段逐项等待原因

P-04 实测通过后，快照需要给出准备循环当前未满足的条件（遮挡、独占全屏、纯黑、页面不对、失焦）。实测前不做。

## R-04 扫描耗时与预计耗时

检查点里已有开始与结束时间、结束类型和覆盖结论（`internal/record/checkpoint.go:270-274` 的 `StartedAt`、`EndedAt`、`Termination`，覆盖见 `:209-212`）。缺的是两件事：一是列表级摘要，不加载整条记录就能拿到这些值（与 R-06 一起做）；二是服务层据此算出“最近 3 次正常结束且覆盖全部的扫描耗时中位数”和依据次数（[09 §4.8](09-window-and-interaction.md#48-06-3-待定项的建议值)）。档位目前首版只有 1920×1080 一档，后续开放新档位时，预计耗时只应取同档位的记录。`RecordInfo.SavedAt` 只是最新检查点文件的修改时间，不能代替结束时间。

## R-05 故障码的中文原因与处理方法

需要一张故障码 → 原因、怎么做、出口（对应的准备检查项 / 去清理 / 复制诊断信息）的映射，供准备检查、摘要、结束通知和诊断共用，覆盖 [T2 §3.2 故障码表](../../specs/t2-platform-capture-input.md#windows-扫描前预检w2b权威说明)和 [05 S3/S6](05-state-matrix.md#s3-扫描准备点开始后w2a-步骤-45) 出现的全部码。现有 `internal/ui/session_status.go:87-170` 只映射了一部分（D-04）。`dpiVirtualized`、`dpiCheckUnavailable` 的用户处理方式规格未写（S3 待定行），需要先在 T2 补上。

## R-06 记录摘要元数据

记录列表每行需要（扫描页不再有最近记录卡，回访者靠列表最前一行判断上次结果）：开始时间、结束类型、覆盖结论、四类计数与可导出数、不完整号位数、截图占用、可读状态（损坏 / 版本不支持 / 无有效检查点 / 中断恢复）。现在 `RecordInfo` 只有 ID、修订、保存时间与占用；要得到计数必须加载整条记录。需要在保存时写一份摘要（或建立索引），让列表不必逐条加载。

## R-07a 行裁剪与表单字段的对应

现有证据每件只有两类图（`internal/app/deliverer.go:254-259`）：

- **文字行裁剪**：套装名、等级、主词条、副词条 1–4 各一张，按阅读顺序；
- **`Context` 裁剪**：稀有度徽标、选中格边框、详情与列表中的装备者头像（`internal/app/payload.go:38-42`、`internal/game/zzz/collect/inventory.go:259-265`）。

没有整块详情面板的图。每张行裁剪的角色（`name`、`level`、`main`、`sub1`…`sub4`）已随观测持久化（`internal/app/payload.go:10-19`，界面层读取见 `internal/ui/recordview.go:75-101`），但 app 层刻意不解释角色的字段含义（`payload.go:30-36`）。

需要的是一张“角色 → 表单字段”的映射：`name` → 套装，`level` → 等级，`main` → 主词条与数值，`subN` → 第 N 条副词条；装备者 → 装备者头像裁剪；没有对应裁剪的字段（如管理状态）明确标为“无截图”。逐件视图据此在点选字段时高亮并滚动到对应的行裁剪（[08 §3.1](08-screens.md#31-三个区域)）。

第三阶段的两个实施提示：

- `Context` 裁剪的角色也已持久化（`internal/app/payload.go:92-95` 的 `context`），但界面层的观测文档只读取 `lines`（`internal/ui/recordview.go:89-94` 的 `observedDoc`），“装备者 → 头像裁剪”要先补读 `context`。
- 证据写入会跳过空图（`internal/app/deliverer.go:242-244`），而界面层现在按下标把第 i 行配给第 i 个证据 ID（`internal/ui/results_view.go:1272-1273`，`:1217` 把 `len(Lines)` 之后的 ID 当作 `Context`；这一约定写在 `internal/ui/recordview.go:62-63` 的字段注释里），跳过时会错位。写入失败同样不追加 ID（`deliverer.go:245-250`），也会错位。应按证据 ID 里的行号配对（`deliverer.go:581-583` 的 `<序号>-line<i>`，`Context` 为 `<序号>-context<i>`，`:588-590`）。

这是 P0：首版不采集面板图时，行裁剪列表就是校对屏的全部证据，“字段能对应到证据”（P-11 第②层）只能靠这张映射实现。**退路**：某件缺少角色（如旧记录或开发数据源）时，按采集顺序列出全部行裁剪、不高亮，也不画框。

## R-07b 采集并保存详情面板图

T1 §1 与 F-18 写的“上下文截图”需要每件额外保存一张详情面板图，这会改变采集与存储（[架构 §5 本地目录](../../specs/scanner-architecture.md#本地目录保留与清理)只保存裁剪证据，面板图仍是裁剪，但大得多）。

存储估算（按 1920×1080 参考布局的像素推算，未实测 PNG 压缩率）：现有 7 张文字行裁剪合计约 5.6 万像素（`internal/game/zzz/collect/reference.go:357-365` 的行区域）；覆盖这些行与装备者头像的外接框约 370 × 434 ≈ 16 万像素，约为行裁剪的 2.9 倍。真实的详情面板比这个外接框更大，比较基数也没有算 `Context` 裁剪，所以这是下限：每件的文字证据占用**至少**变为现在的约 3.9 倍；一次 1,017 件的全量扫描按同一比例增加。截图默认永久保留（C-28、P-13），增量会一直累积，直到用户手动清理。

是否采集由用户决定（[11 Q-06](11-phase2-open-questions.md#q-06-是否采集详情面板图)）。采纳时为 P1，并需要同步架构 §5 的证据清单、T5 §6 的证据说明和存储估算；不采纳时，逐件视图按 R-07a 只显示行裁剪列表。

## R-08 四类件的统一分类与计数

“待补录 / 待校对 / 有警告但可导出 / 已通过”和“待处理”需要在服务层按同一判定顺序计算（[README 术语](README.md#术语)），供摘要、件列表、结束通知、导出对话框共用。现在分类在界面层（`internal/ui/counts.go:29-46`），而且没有“有警告”这一类；结束通知在界面之外也需要这些数字。

## R-09 两段式通知的触发事件

需要两个可靠的边沿：输入许可关闭（第一段）与收尾结束或保存失败（第二段），并带上第二段需要的结束类型、覆盖结论、待处理数、可导出数、首个故障码。快照里已有 `InputPermitted`、`Phase`、`End`、`SavePending`、`SaveError`，原则上可推导，但通知要求：准备超时（从未开放输入）不发第一段；同一次收尾的保存失败只通知一次（按 [11 Q-04](11-phase2-open-questions.md#q-04-保存失败的通知频率06-3-第-16-条) 推荐 A 写入，待用户确认；[09 §4.8](09-window-and-interaction.md#48-06-3-待定项的建议值)）。这两条需要服务层给出明确的“这次会话是否开放过输入”和“本次收尾第几次保存失败”。

## R-10 号位级结论

摘要和通知要写“3 号位、5 号位不完整”及原因。现状没有：`Coverage` 只有 `Status` 与 `ExpectedCount`（`internal/record/checkpoint.go:209-212`）；`ObservedScope`（`:266-269`）是遍历预检观察到的筛选、排序、数量快照，不是逐号位结论。需要记录中保存稳定的号位编号、每个号位的结论与原因码，以及排序是否验证。摘要标题（[08 §2.1](08-screens.md#21-结论区的写法)）和第二段通知都依赖它。

## R-11 扫描中的被动进度

窗口恰好可见时（4K 并排）显示当前号位与已采集件数。计数已在内核快照 `Counts` 中；当前号位没有。按设计假设这一项不影响主流程。

## R-12 记住窗口位置与尺寸

用 MyGo 的 `WindowOptions.StateKey` 实现（`window.go:166-173`）：它在窗口关闭和应用退出时保存位置、尺寸、最大化与全屏状态，下次用同一键创建窗口时恢复。另有 `Window.Position()`、`Window.Bounds()`（`window.go:901`、`:840`）可以读取当前位置。

恢复条件与回退（`window_state.go:122-149`）：

- 窗口与某个显示器的**工作区**至少重叠 100 × 50（窗口更小时按窗口尺寸）就按原位置恢复，因此窗口可能大部分在屏幕外，不只是“部分落在任务栏下”。
- 条件不满足时窗口居中，但**尺寸保留上次的值**（按主显示器工作区裁剪），最大化与全屏状态照样恢复。

这可以接受：youkai 自己的窗口不受 C-12 约束，至少有一块可见时用户能把它拖回来；09 §1 已按这两点描述。

## R-13 诊断信息的组装

“复制诊断信息”需要一段可读文本：版本、系统版本、显示配置（分辨率、缩放）、最近一次扫描的结束类型与故障码、首个触发与阶段；不含外部窗口标题（[T2 §3.2](../../specs/t2-platform-capture-input.md#windows-扫描前预检w2b权威说明)）。“打开诊断目录”使用现有日志目录（[开发指南 诊断日志](../../development.md#诊断日志)）。

## R-14 开始受阻的原因

`Snapshot.Busy` 只说明槽位被占。开始按钮旁的说明需要区分：上次扫描仍在收尾、待重试保存、导出进行中、校对保存进行中、正在安装更新、正在退出（S2 对应行）。其中导出与校对保存由界面层自己知道，其余需要服务层给出。

## R-15 界面语言固定为简体中文

启动时用 `App.SetLanguages("zh-Hans")` 或 `App.SetLocale("zh-Hans")` 固定 MyGo 内置控件的语言（`locale.go:83`、`:147`；`locales/` 下有 `zh-Hans`），不跟随系统语言（C-29、现状 M3）。属于应用外壳，不是服务层，但同样是第三阶段的实施项。

## R-16 只重扫不完整号位并合并

P-12 已采纳为方向，首版不实现。它对契约的影响已在 [06 P-12](06-proposals-and-phase2.md#1-功能提案) 列出：一条记录由多次会话组成后的封存、序号、来源会话与修订；合并后的覆盖结论如何说明各号位的采集时间；JSON 的来源会话与计数；只能按号位整体替换。界面上本阶段只在摘要的“重新扫描”一行预留位置（[08 §2.1](08-screens.md#21-结论区的写法)）。

## R-17 一键提权

P-05 实测通过后才设计：以管理员身份重新启动自己，并把单实例、数据根占用、自动更新交接给新进程。实测前准备检查只给文字引导和“退出 youkai”按钮。

## R-18 首次隐藏提示的已读状态

偏好里记录首次隐藏提示是否已确认，设置 › 常规可以重新打开（P-10、F-40）。

## R-19 启动失败的用户可见提示

数据根被占用或无法打开时，现状只写日志就退出（`cmd/youkai/main.go:89-91`），用户看到的是“双击没反应”。同一版本的第二次启动先拿单实例锁并交给已运行实例（`main.go:85-87`），不会走到这里；走到这里的是单实例身份不同的另一个 youkai 进程（例如开发版）占用了数据根，或数据根的其他错误。两种情况要分开文案（[08 §10](08-screens.md#10-启动失败)），所以占用检查需要返回可区分的原因。

实现前提：MyGo 的 `Dialog.Error`（`dialog.go:228-230`）在 `App.Run` 之前、在主线程上调用会 panic（`app.go:128-131`），而占用检查现在就在 `App.Run` 之前。需要调整启动顺序（先 `App.Run`，在 `App.WhenReady` 里报错再退出；单实例处理函数仍在 Run 之前注册，`main.go:97-100`），或改用不依赖 MyGo 的系统原生消息框。这需要改启动流程与服务层，不只是界面文案。

识别资源缺失不属于启动失败：启动本身不加载模型（F-05），它作为准备检查的一项交给界面（与 R-01 一起）。
