## 依据与写法

- **功能以现有规格为准。** 权威来源：[T1](../../specs/t1-mygo-ui-distribution.md)、[T6](../../specs/t6-review-export-workflow.md)、[架构 §5/§6](../../specs/scanner-architecture.md#5-扫描会话与结果语义)、[T2](../../specs/t2-platform-capture-input.md) 的平台约束、[JSON/CSV v2](../../specs/scan-json-format.md)、[发布与自动更新](../../release.md)。规格没写清的地方，对照 `internal/ui`、`cmd/youkai` 和 `internal/app` 的实际能力，以 `file:line` 引用（基于 `main` 的 `f23c836`）。
- **单一事实来源。** 这里只写用户视角的归纳和指向规格的链接，不复制规格正文；规格变化时以规格为准，本草案随之修订。
- **提案与正文分开。** 增删或改变功能的提案集中放在 [06 第 1 节](06-proposals-and-phase2.md#1-功能提案)，每条标明状态。“待用户决定”的提案不进入正文；2026-11-03 已决定采纳的提案，正文按决定来写并标注编号，对应规格尚未同步。
- **旧材料的用法。** [2026-10-21 设计基线](../uiux-2026-10-21/README.md)已过时，本阶段不引用其布局。2026-11-03 的现状评审只当作“现状问题清单”，用于核对新旅程是否覆盖了那些痛点（见 [06 第 2 节](06-proposals-and-phase2.md#2-现状痛点覆盖核对)），不作为设计基础。
- **核对方式。** 行为依据来自规格与代码阅读；本阶段没有另行运行应用。现状评审时曾在 Mac 上用开发数据源运行过一次，那次的观察只用于痛点核对。

## 术语

本草案统一使用以下说法，第二阶段的文案可以再定：

- **扫描**：从点击开始到收尾保存完成的一次会话，阶段为准备 → 采集 → 收尾 → 已结束（[架构 §5 生命周期](../../specs/scanner-architecture.md#生命周期)）。
- **记录**：一次扫描在本机保存的结果，可从历史重新打开。
- **件**：一件驱动盘（一条观测）。
- **件的四类**：待补录、待校对、有警告但可导出、已通过；判定顺序为“处理结局 → validation → quality → warning”，每件只落入第一个命中的类。定义与边界见 [T6 §2 件的四类与判定顺序](../../specs/t6-review-export-workflow.md#件的四类与判定顺序)。
- **可导出**：满足 [T6 导出规则](../../specs/t6-review-export-workflow.md#3-保存重新查看与导出建议)的件。
- **准备检查**：开始扫描前常驻的条件清单，每项显示“当前值 → 需要值”（P-03）。
- **结果摘要**：扫描结束后回答“扫全了吗、能直接导出吗”的结论视图内容（不是布局）。
- **覆盖结论**：全部 / 部分 / 无法确认（[架构 §5 完整性与身份](../../specs/scanner-architecture.md#完整性与身份)）。
