## 结论摘要

- 保留 Go + MyGo、ONNX Runtime + PP-OCRv6 small、ScreenCaptureKit/Quartz、GDI/SendInput 的现有技术栈，也保留现有串行控制骨架。**不做一次性重写**，按阶段替换遍历证据模型。
- 目标形态：**同帧特征（含选中框、质量与来源）→ 连续位置验证 → 账本提交 → 完整性核验；失配时有界重新建立位置证明或回顶重走**。
- K1 把“按内容重定位”改成“重新建立位置证明”：账本主键是位置 + 绝对行 + 列 + 尝试；内容指纹只筛候选，候选唯一才继承已采集状态。F6 表明整屏缩略图/详情特征无法唯一对应，因此实际恢复以“回到已证明顶部重走”为主；仍无法建立则把该位置标为不完整，继续后续位置，最终报部分（会话致命故障除外）。
- K2 以“选中框的视口内位移”为主要滚动证据，像素/特征匹配降为辅助核对；停稳模型必须先观察到移动开始，再判停稳。F7 显示拖动后 0–500ms 不动、约 1s 才开始动、2s 仍在动（迟到+惯性），预算与时间按客户端 profile 标定。
- K3 的选中驱动推进（边缘点击/键盘）只在对应客户端实测通过后启用。macOS 云客户端点击末行与键盘均不能推进（F2/F3），继续用拖动；Windows 两客户端待 F8。任何动作都要闭环确认实际位移，动作未决不得换另一种输入补救。
- K4 完整覆盖由范围证明（单次面板访问内重置→勾选 S→滚动面板到底检查全部控件→关闭；选中按蓝色填充判断）、到顶、每位置连续覆盖、每个占用格位有结局、到底证据推出；不要求排序方向，改为要求排序标签不变 + 连续覆盖。当前界面不显示数量，结果明确注明“本次未做计数对账”，不因缺少计数而降低覆盖。
- 2026-10-29 真机核实（macOS 云）：F1 可见界面无数量；F2/F3 点击与键盘不推进；F4/F4b 可证明 S、套装、状态、主/副属性与底部两个控件的清空，方向不可读；F5 选中框可用于滚动位移；F6 内容不能唯一重定位；F7 拖动迟到+惯性。F8 未做。
- K5 把故障分为物品局部、可重试动作、可重建位置、会话致命四类；区分未投递、效果已确认、已投递效果未知，效果未知先重新观察或定位再决定动作。
- 三客户端（macOS 云、Windows 云、Windows 完整客户端）共享安全规则与账本，分离布局、遮罩、噪声范围、时序与导航能力；三个客户端分别验收，Windows 实测时间另行安排。
- 暂不做跨重启续扫；先做同一次扫描内的有界恢复，三客户端验收后再单独评审跨重启。

见 [Kimi 评审会话](lody://session/ab09f5ca-0ffc-4cf8-b5af-ef08b9175a82?workspace=jh71jrcd7n3s48y9vbscr9p8w98dgyyz)。

**[控制者提供]** 2026-10-28 的消融实验结论是：安全逻辑（不猜、不去重、失败即停等）的测试覆盖较好；感知阈值此前没有被测试约束，已由 [#93](https://github.com/LoTwT/youkai/commit/e249db3) 补测试。

### 1.2 动作状态机缺陷：效果未知时再次拖动

**[事实]** `awaitScroll` 的终局汇总只有三条分支：已有 candidate 但未停稳、见过 `Lost`/ambiguous、见过 `Stationary`；没有显式的 `Undecided` 状态。`Undecided` 帧不会清除此前的 `sawStationary`/`sawLost`/`sawAmbiguous`，因此“先见过 Stationary、后又出现 Undecided”会在预算到期时汇总成旧的 `Stationary`；本次现场是同一缺陷的另一种表现：5090 在基准后 8232ms 到达，处于第二次拖动后的等待中，先判 `Lost`（可见），其后的可见 34 帧 `Undecided` 没有清除此前的 Lost/歧义状态，终局因此仍是 `lost`。

见 [inventory.go:2808](../../internal/game/zzz/collect/inventory.go#L2808) 的 `finish`、[inventory.go:2816](../../internal/game/zzz/collect/inventory.go#L2816) 的 `sawLost` 汇总与 [inventory.go:2948](../../internal/game/zzz/collect/inventory.go#L2948) 的判定 switch（[inventory.go:2954](../../internal/game/zzz/collect/inventory.go#L2954) 处理 `sm.Lost`）。日志的 `outcome=lost` 与 “no unique correspondence verified” 文案就是这个汇总路径的结果。

**[事实]** `scroll()` 在尝试循环外取 `before`（[inventory.go:2574](../../internal/game/zzz/collect/inventory.go#L2574)），重试时仍用同一个旧基准拖动并比较；每次 `awaitScroll` 又新建 trace（[inventory.go:2791](../../internal/game/zzz/collect/inventory.go#L2791)），`waitOut` 被覆盖，诊断只保留最后一次等待。见 [inventory.go:2604](../../internal/game/zzz/collect/inventory.go#L2604)。

**[事实]** `scroll()` 在 `out.stationary` 和默认的无明确终局分支都会再次拖动（[inventory.go:2692](../../internal/game/zzz/collect/inventory.go#L2692)、[inventory.go:2699](../../internal/game/zzz/collect/inventory.go#L2699)）。默认分支正是“没有可验证终局”，也就是动作效果未知；此时再发一次拖动，违反 T5 “首次动作效果尚不明确时，不发送验证用的下一次动作”的约束（[T5 §4](../specs/t5-zzz-inventory-traversal.md#4-一件物品何时可以进入识别队列)）。

**[事实]** 最新失败日志为 `attempts=2`、`drag_ms=2812`、`settle_ms=10023`，与“两次 5 秒等待”一致。第一次尝试的帧/判定仍未被保留；第二次拖动后的等待中可见 5090 `Lost` 与随后可见的 34 帧 `Undecided`（5096→5154 间有帧被保留策略丢弃，总计 `dropped_frames=8`，判定不可见）。状态机允许在 `stationary` 和无明确终局分支再次拖动，且第二次仍用旧基准；两份评审都指出了这一限制。

**[推断]** 由 `unsettled=false` 和终局 `lost` 只能推出被丢弃帧中没有带唯一对应的 `Displaced`；最后一个非 `Undecided` 判定是 `Lost` 或歧义 `Displaced`（可能是 5090，也可能是某个被丢弃帧），不能排除其中先有 `Stationary`。终局 `lost` 来自此前的 Lost/歧义状态（可见的是 5090）未被后续可见 `Undecided` 清除，而不是 34 帧都没有判定。

**[推断]** 1.1 与 1.2 的叠加方式：1.1 的绝对阈值使可见的 5096–5357 34 帧正确 4 行位移全部落在 `Undecided`，无法形成 candidate；1.2 的粘滞状态使此前的 Lost/歧义状态（可见的是 5090）不被后续可见 `Undecided` 清除，`finish` 因此把终局标成 `lost`。只修 1.1，可见的 5096+ 帧会变成 `Displaced` 并可能停稳；只修 1.2，仍然没有可提交的 candidate，扫描仍不能完成。两者必须都修。

**[推断]** 这条缺陷把一次未决的滚动放大成两次拖动叠加、旧基准比较和首次证据丢失；不能只在 K5 上增加重试。

### 1.4 现有完整性与测试覆盖的缺口

**[事实]** 架构要求全部覆盖同时具备范围、起点、排序、连续遍历、末端证据和可用的同范围总数（[架构“完整性与身份”](../specs/scanner-architecture.md#完整性与身份)）。

**[事实]** T5 的实现口径写成了“若存在可信的同范围计数，与遍历账目一致”（[T5 §5](../specs/t5-zzz-inventory-traversal.md#5-滚动衔接重复物品与末尾)），因此当前可以在没有可信计数时仍声明 `complete`。在新决定下，这一行为不再是待修复的缺陷，而是与“当前界面不显示数量”相匹配的产品选择；需要改的是架构原文的计数要求。

**[用户确认 2026-10-28]** 当前游戏界面**不直接显示数量/容量**。因此本文不再把计数作为完整覆盖的必要条件：完整覆盖改为“范围已证明 + 到顶 + 每位置连续覆盖 + 每个占用格位有结局 + 到底证据”，结果中注明“本次未做计数对账”。这与架构 §5 原文“完整覆盖需可用的同范围总数”不同，属于**有意放宽**，已在 2026-10-29 同步到架构与 T5；将来若取得可信的同范围计数，再增加对账，混合稀有度的全仓总数不能冒充 S 级总数。

**[事实]** 当前 S 筛选只验证漏斗 `Active`，S 控件选中态没有像素探针；排序探针只验证“稀有度”标签，不读取升降序方向（[T5 §3](../specs/t5-zzz-inventory-traversal.md#3-开始前必须核对的页面条件)）。因此“范围成立”目前弱于“漏斗亮着”。

## 2. 选型复核

| 选型 | 结论 | 依据与代价 | 触发重新评估的条件 |
| --- | --- | --- | --- |
| Go + MyGo | **保留** | 当前失败没有指向 UI 框架、构建或分发；MyGo 已承担窗口、交互与打包。 | MyGo 的图片/长列表/输入法或分发在两平台实测中成为主要瓶颈，且无法在现有边界内解决。 |
| ONNX Runtime + PP-OCRv6 small | **保留** | 以 [ocrlayout.go:6](../../internal/ocrlayout/ocrlayout.go#L6) 常量为准：ORT 1.29.0、`PP-OCRv6_rec_small.onnx`。背景材料里的“PP-OCRv5”是旧称/参考实现说法，不是本仓库当前模型。千件级采集已证明 OCR 主路径可用。 | 独立验收集出现不可接受的自动接受错误或拒识率；原生推理崩溃、终止超时或持续泄漏；需要换模型/换后端才能满足三客户端质量门槛。 |
| ScreenCaptureKit + Quartz（macOS） | **保留** | 已有窗口流、几何与输入实测；本次失败是感知判定，不是采集失效。 | 受支持配置上持续黑屏、旧帧、帧时间不可用或成本过高；届时再比较其他 macOS 窗口采集路径。 |
| GDI + SendInput（Windows） | **暂时保留** | Windows 仍是计划内客户端，但遍历尚未实测；SendInput 受 UIPI 限制，输入成功不等于游戏响应。 | GDI 在正确裁剪下持续黑屏、返回旧帧或性能不足时，再评估 WGC；WGC 提供窗口帧和系统时间，但仍不能证明云端动作完成，且增加 WinRT/D3D 集成成本。 |
| 引入 gocv/OpenCV | **否决（暂不引入）** | 当前需要的是遮罩、降采样、归一化相关、梯度/边缘和候选竞争，Go 标准库与现有像素代码可以完成；引入 OpenCV 会增加 C++ 原生构建、签名、双平台分发与调试成本。 | 手写配准/检测代码明显变大且难以验证，或出现必须依赖成熟几何配准/检测算法才能跨客户端稳定的场景；届时按收益/成本重新评估，不是永久禁止。 |
| 检测/分类模型 | **暂不引入** | 可能改善格子、选中框、角标和滚动条提取；但需要三客户端标注与独立验证，且**不能给重复物品创造身份**，不能解决 K1 的实例歧义。 | 选中框、格位或滚动条在多个受支持画质下难以稳定提取，且小模型（可复用 ORT）的收益超过标注与验证成本。 |
| 外部数据途径 | **不采用** | Enka 的公开结构是展示角色装备（`EquippedList`），不是完整仓库，见 [Enka ZZZ API](https://github.com/EnkaNetwork/API-docs/blob/88fc20697fda924430943434c11e0c45eb39509f/docs/zzz/api.md#equipment)。抓包（如 [zzz_packet_capture](https://github.com/AleXu224/zzz_packet_capture)）需要登录流量、相应权限和随版本维护的成本，未证明适用于 macOS 云客户端；内存读取/注入在云客户端不可得，且带来兼容性、反作弊、安全和维护风险。 | 用户明确改变产品范围并接受新的授权/安全边界；在此之前不把外部数据当作扫描替代或身份来源。 |
| 录像/截图导入 | **仅开发与回放** | 有利于失败回放、回归和人工救援；不替代实时扫描，也不作为用户可用数据来源。 | 仅在开发/验收工具范围内扩展，不进入首版产品导出或自动扫描路径。 |

**[推断]** “保留技术栈”不等于“三个客户端都已验证”。Windows 的遍历、布局和输入仍是未完成证据；选型复核的结论是“当前没有证据要求更换”，不是“已经证明三客户端可用”。

## 4. 决定：修正后的 K1–K5

### 4.1 总体形态

保留现有串行控制骨架：一个控制者按“选择 → 验证选择 → 等待就绪 → 采集”推进，平台与 OCR 仍按现有边界工作。替换的是遍历证据模型，不是一次性重写整个扫描器。

```text
同帧图像
  → 感知：格子/行签名、选中、详情指纹、滚动条、计数（若界面提供）
  → 连续位置验证：行重叠、选中锚点、滚动轨迹
  → 账本提交：位置 + 绝对行 + 列 + 尝试
  → 完整性核验：范围 + 顶部/连续/底部（计数可选）
        失配 ↙
  有界重新建立位置证明（唯一候选继承 / 回顶重走）
        失败 → 该位置标不完整，继续后续位置，最终报部分
```

设计原则：

1. **证据优先于速度。** 不因“看起来像同一件”而跳过格位，不用 OCR 成功数推断覆盖。
2. **动作闭环。** 每次输入后先观察实际效果，再决定下一个动作；效果未知不叠加动作。
3. **最小替换。** 先在现有 `Matcher` 和 `scroll()`/`awaitScroll` 接缝内改判定，再引入账本与恢复；每阶段合并后扫描仍可用。
4. **客户端分离。** 共享安全规则、账本和故障分类；布局、遮罩、噪声、时序和导航能力按客户端 profile 分离。
5. **保留原始证据。** 每次尝试的输入、帧、判定和失败原因都保留；不能用最后一次覆盖第一次。

### 4.2 K1：重新建立位置证明

**决定：** 不把“可重定位”定义为“通过物品内容找到它原来在哪一行”。改为：当连续位置验证失效时，重新建立**位置证明**；内容特征只用于缩小候选。

- **账本主键：** `位置 + 绝对行 + 列 + 尝试`。位置是转盘 1–6；绝对行从已证明的顶部起算；列是当前视口内的 0–3 列；`attempt` 区分本次会话内的遍历/恢复尝试，不是物品身份。
- **内容指纹：** 格子缩略图签名、行签名、详情指纹只用于筛候选。它们不能证明“两件盘相同”，不能跨格位合并、删除或跳过观测。
- **继承条件：** 当前可见内容在账本中只能对应**唯一**候选时，才允许继承该候选的已采集状态；继承只免除重复接纳，不免除当前帧的占用、位置连续性和范围核验。候选不唯一时，可用相邻行/滚动轨迹消歧；仍不唯一则回到已证明的顶部重走；重走仍无法建立位置证明时，把该位置标为不完整，继续后续位置，最终报部分。
- **禁止：** 不得按指纹匹配直接跳过格位，不得把两个观测合并成一件，不得用计数反推“缺的那一件在哪一行”。计数只能证明数量，不能提供位置身份。
- **选中框为主证据：** 拖动前选中视口末行的一格；拖动后由选中框所在行计算位移（例如 r4c3 → r0c3 为 4 行）。滚动步长必须保证选中格仍在视口内；选中框滚出视口时不能继续用它证明位移，改用像素/特征或滚动条辅助核对，仍不足则按位置丢失处理。F5 的 4 行末行锚点由 2026-10-28 现场诊断帧证明；两组日志结局均为 `lost: unsettled=true`，after 帧是未停稳的候选帧，且诊断帧只裁列表区，不能据此证明详情不变或停稳后的位置。F6 表明内容特征不能替代该证据。
- **重访：** 只有尚未确认采集的失败（如详情归属未确认）才稍后重访；重访成功，新观测取代旧观测，结果只算一件。重访在接纳前截住，不分配 `sequence`；旧 attempt 只留诊断，不计入任何件数（不进 `excludedCount`）。已采集但 OCR/字段有问题的件交给现有逐件校对流程，不重访。JSON v2 的计数等式不变，见 §9.4。
- **重走：** 回顶重走必须重新证明顶部、范围与排序标签不变；重走时继承已解决格位要逐行/逐格核验当前内容，不能只靠旧截图或旧绝对行。F6 表明内容不能提供唯一候选时，不能把旧行图当作实例身份；直接回顶重走或把该位置标为不完整。

**[推断]** 这条决定与“不去重、不猜”一致：内容特征可以帮助“找候选”，但不能单独承担“这就是同一件”的结论。真正相同的相邻盘仍各算一件；无法消歧时宁可把该位置标为不完整并继续后续位置，也不合并观测。

### 4.3 K2：感知

**决定：** 把“整视口灰度 MAD + 绝对阈值”升级为“选中框位移为主、同帧遮罩、归一化特征与最佳对次优竞争辅助、多帧停稳”的组合判定。

- **同帧：** 格子签名、选中框、详情、滚动条和计数（若界面提供）必须来自同一帧或明确绑定的帧 ID；不把不同时刻的特征拼成一次判定。
- **选中框位移（主要证据）：** 拖动前选中视口末行一格，拖动后读取选中框所在行，按行距换算位移；要求选中格始终留在视口内。F5 的 2 行拖拽 4/4 跟随与 4 行末行锚点（r4c3 → r0c3）支持选中框位移；4 行锚点的两组日志结局为 `lost: unsettled=true`，after 帧是未停稳候选，只证明位移，不证明停稳或详情不变。
- **遮罩：** 动态选中框、鼠标悬停等变化区域遮掉；装备头像、管理状态角标等**可区分证据分通道保留**，不能为了降噪把所有角标都遮掉。遮罩范围按客户端 profile 标定。
- **归一化特征：** 使用归一化相关、梯度/边缘或等价的尺度无关特征；在可比的支持区域上比较。均匀图像、低信息量区域不能因为“最佳候选分数高”而接受。特征匹配降为辅助核对：不得单独用绝对误差阈值否决选中框与滚动条一致的位移。
- **最佳对次优竞争：** 不仅看最佳候选的绝对分数，还要求最佳与次优整行/整格候选有足够差距；差距不足时保持未决。（2026-10-31 澄清：这里的“差距不足”指特征不能单独裁决，不禁止独立证人。选中框与 NCC 指向同一行、该行达标，但差距低于 0.05 时，滑块的方向与行程可作为独立证人裁决；候选超过选中行超过并列容差 ε=0.005 才算特征与选中框矛盾，ε 内的并列/近似并列交由滑块，且滑块行程还必须与其他未被排除的同向候选行数可区分。特征仍不得单独接受差距不足的位移；ε 的依据与风险分析见 T5 §5。）
- **多帧停稳：** candidate 必须相对自身连续观测稳定，不能用“相对拖动前帧仍是同一行数”代替停稳；迟到惯性、云视频重复帧和底部回弹都要纳入停稳模型。F7 的拖动在 0–500ms 保持不动、约 1s 才开始移动、2s 仍在移动，故必须先观察到“移动已开始”，再以连续帧/选中框/滑块判停稳；2s 内无移动不等于动作未生效。预算与时间按客户端 profile 标定。
- **保留拒绝条件：** 信息量不足、重叠少于一整行、画面运动超出模型（窗口/几何/页面变化）时拒绝，不进入候选竞争。
- **阈值与验收：** 阈值按客户端 profile 标定；调参集与封存验收集按**完整扫描**划分，同一扫描的相邻帧不得跨组。现场失败序列可以进入调参集，但必须另采完整扫描做独立验收。阶段 2 用应用诊断记录精确帧时间，不另做独立时序重测。

**[评审]** Kimi 的 NCC 复核只说明“正确对齐与错误候选在归一化特征上可分”，不构成阈值验收；Sol 也强调特征签名同样需要阈值，模糊画面也会产生最佳候选，不能只凭排名接受。

### 4.4 K3：推进方式

**决定：** 选中驱动（边缘点击、方向键、`d` 键等）是候选路径，不是默认路径；只有对应客户端实测通过后才启用。

- **动作闭环：** 任何动作（点击、拖拽、键盘）都要在动作后确认实际位移/选中变化；不能“点了就假定一行”。
- **动作未决：** 上一次动作效果未知时，不得切换另一种输入方式补救（例如点击未确认就改拖拽）；先重新观察或定位，仍无法确认则重建位置；仍失败则该位置不完整并继续后续位置（会话致命除外）。
- **macOS 云客户端（F2/F3）：** 点击末行只改变选中、不移动列表（6/6，含顶部、第二视口与短列表、首/末列）；方向键、`d` 键与右方向键均不移动选中（Escape 正常，说明按键可投递）。因此该客户端不使用边缘点击或键盘推进，继续用拖动；选中框仍用于当前视口内的位移证据。
- **Windows 两客户端：** 点击/键盘推进均未实测（F8）；取得证据前保留拖拽或拒绝，不共享 macOS 的结论。
- **每个客户端一条已验证路径：** 拖拽仍是基线；边缘点击/键盘推进按客户端分别验证（F2/F3/F5）。未验证的客户端保留拖拽或停止，不共享“某个客户端有效”的结论。
- **坐标事务：** 边缘点击可能带动列表；点击前的坐标和点击后的位置必须分开记账，旧坐标不能直接用于下一次点击。

### 4.5 K4：完整性

**决定：** 先证明范围，再核对覆盖与末端证据；计数不是完整性的必要条件。

完整覆盖的必要条件（缺一即 `partial`/`unknown`）：

1. **范围：** S 选中态有直接证据（蓝色填充，不只是漏斗 `Active`）；其他筛选在**单次面板访问**内按“重置→勾选 S→滚动面板到底检查全部控件→关闭”核验并记录；排序标签在扫描期间保持不变。不要求读取排序方向；方向变化只能由“排序标签不变 + 连续覆盖”间接约束，不作为完整性条件。
2. **顶部：** 稳定非移动的顶部确认；不能以“向上滚了很多次”代替。
3. **连续覆盖：** 每个位置的每次移动都有可解释的位置对应；不允许无法解释的跳跃。
4. **每个占用格位有结局：** 每个占用格位有 S 接纳、非 S 跳过或未解决结局；未解决不能消失或被静默跳过。
5. **底部：** 独立底部证据（最后一步不足整步、或 `Bottom + Stationary`）。
6. **重复物品：** 相邻且详情完全相同的 S 盘各算一件；参照往返只解决“详情是否属于当前目标”，不建立跨视口实例身份。

**F4/F4b 证据与边界：** 筛选面板的 S 芯片有蓝/灰可区分选中态；套装“点击选择”为空；状态 4 个 chip 均灰；主属性可见 chip 无蓝色；副属性展开为两列五行 10 个 chip，清空以“无蓝色填充”判定。面板可滚动，滚到底新增“符合副属性词条数量（1–4）”与“排除筛选”两个控件；没有槽位或等级筛选（槽位是仓库页右侧转盘，不是面板筛选）。主属性只核对可见标签；2 号位仅“攻击力”属正常（该位主属性固定为攻击力），4–6 号位多主属性留到阶段 3 采样。橙色文字疑为当前角色推荐标记（未独立验证），不能作为选中态；判定选中必须看蓝色填充。排序下拉右侧的“⇅”按钮可能是方向控件，仅记录，不作为完整性条件。副属性尚无“选中→取消”的正面对照，留到阶段 3 采样；严格“重置→勾选 S→滚动面板到底检查全部控件→关闭”的顺序在 F4b 中有程序性缺口（实际为滚动、重置、关闭后重开勾选 S），阶段 3 的实现与验收必须按完整顺序执行。

**排序标签的两种失败（2026-10-29 用户决定）：** 准备阶段排序标签无法验证（未读到或模板不匹配）属于范围证明失败，按位置准备失败处理：该位置跳过、记录原因，继续下一个位置；扫描期间观察到排序标签变化——即使新标签仍可读——停止整次扫描并撤销完整结论。扫描器从不修改排序，变化意味着有人操作了游戏，继续扫描不安全。

**覆盖与结果完整分开：** 所有位置都走完（范围、顶部、连续覆盖、每格结局、底部成立）时，`coverage` 仍可为 `complete`；未解决格位在可用结果/导出中如实标注，不能因为 `coverage: complete` 就把未解决件当作可用。

**计数（可选，不是必要条件）：** 用户于 2026-10-28 确认当前游戏界面不直接显示数量；F1 在仓库页标题区与筛选面板可见范围内也未发现数量/容量读数，用户决定不访问其他页面查找。结果中必须明确注明“本次未做计数对账”；若将来取得可信的同范围计数，再增加对账。混合稀有度的全仓总数不能冒充 S 级总数（T5 已有此规定）；计数只能证明数量，不能定位缺哪一件。

**[评审/用户确认]** Sol 指出旧套装筛选残留时“剩余列表全是 S、读数正确、走到底、采集数一致”仍可能漏扫；Kimi 指出计数只能证明数量，不能定位缺哪一件。用户随后确认当前界面不显示数量，因此本文把计数降为可选对账，而不是完整覆盖的门槛。

### 4.6 K5：故障分级

**决定：** 按故障影响面分级，而不是把所有失败都送进同一个重试/停止路径。

| 级别 | 例子 | 允许动作 | 结果与记账 |
| --- | --- | --- | --- |
| 物品局部 | 单件详情无法归属、单件 OCR/字段失败、单件证据缺失 | 标记未解决，继续当前位置；仅对**尚未确认采集**的失败稍后自动重访；已采集但 OCR/字段有问题的件交现有逐件校对，不重访；成功时新观测取代旧观测 | 结果只算一件；重访在接纳前截住，不分配 `sequence`，旧尝试只留诊断，不计入任何件数（不进 `excludedCount`），JSON v2 的计数等式不变；仍失败则可用结果标未解决，`coverage` 可仍为 `complete` |
| 可重试动作 | 点击未生效、拖拽无位移、选中框瞬时消失、动作迟到但可观察 | 只有明确“未产生效果且无迟到动作风险”时才有限重试；每次尝试独立记录 | 效果未知先重新观察/定位，不直接重发；不得换输入方式 |
| 位置准备失败 | 筛选面板打不开、重置或 S 未生效、面板滚动检查未通过、回顶无法确认、转盘切不到该位置 | 先按“可重试动作”边界重试；效果未知先重新观察/定位，不叠加动作、不换输入方式；仍失败则停止该位置的准备 | 该位置标为不完整并记录原因，继续下一个位置，最终 `coverage=partial`；每个位置重新执行重置/S/范围证明/回顶，前一位置失败不污染下一个位置；该位置此前已接纳物品保留为可用导出、不计入 `excludedCount`（见下） |
| 可重建位置 | 滚动位置丢失、绝对行无法确认、列表仍同范围 | 有界自动重新建立位置证明：唯一候选继承，或回已证明顶部重走 | 预算耗尽仍无法建立→该位置标为不完整，继续后续位置，最终 `coverage=partial`；不猜行数 |
| 会话致命 | 已不在驱动盘仓库页（页面无法验证）、失焦、云断连/`pageUnverified`、窗口替换/`targetLost`、几何变化、权限撤回、采集流停止、存储/证据失败、运行库故障、用户取消、扫描中观察到筛选、排序标签或布局的可观察变化（沿用 T5 既有停止规则；库存数量当前不可观察；排序标签变化为 2026-10-29 再次确认） | 停止输入、收尾、保存已接纳结果 | 停止整次扫描；覆盖保持部分/无法确认；不自动续扫 |

> 覆盖与结果完整分开：范围、顶部、连续覆盖、每格结局、底部都成立时 `coverage` 可为 `complete`；未解决格位只在可用结果/导出中标出。位置准备失败或位置级证明失败只让该位置不完整并继续后续位置；只有会话致命故障停止整次扫描。每次位置重试、物品重访或位置重建的内容都记录在结果/诊断中，供用户查看；位置准备失败必须在结果中记录失败原因。物品局部的重访只针对未确认采集的失败，且在接纳前截住、不分配序号；已采集但 OCR 有问题的件不重访（见 §9.4(a)）。

**范围未证明位置已接纳物品（2026-10-29 用户决定）：** 该位置此前已接纳的物品保留在可用结果与导出中，不计入 `excludedCount`；该位置 `coverage` 报 `partial`，并在结果界面/诊断标注“该位置范围未证明”。公共 JSON/CSV v2 不新增位置级字段，JSON 以 `coverage=partial` 表达；物品本身仍留在 `items` 中。依据：范围证明发生在遍历前，此情况少见；每件物品接纳时单独核对 S 徽章，范围未证明影响的是“是否遗漏”，不是“已采是否正确”。JSON v2 形状与计数等式不变。

动作状态必须区分：

- **未投递：** 平台明确未发送；可以按动作预算决定是否重发。
- **效果已确认：** 位移/选中/详情证据成立；提交并继续。
- **已投递但效果未知：** 先重新观察或定位；在确认前不得发送下一个动作。这条直接对应 T5 §4，也是 1.2 缺陷的修复原则。

**[推断]** “只有无法重定位才停”不成立。失焦、窗口替换、权限、存储和用户取消即使理论上“还能再找位置”，也必须停止整次扫描；位置准备失败或位置级证明失败则只把该位置标为不完整并继续后续位置。K5 的动作由故障类别决定：会话致命停止，位置准备/位置级失败降级并继续，物品局部重访。

### 4.8 安全不变量

以下不变量不因重新架构而放宽：

1. 不按属性、图像哈希或详情指纹去重；相邻同详情盘各算一件。
2. 不猜滚动行数；没有唯一对应就重建位置；仍失败则该位置不完整并继续后续位置（会话致命除外）。
3. 每个已接纳观测恰好一个结局；不重编号、不删除旧观测。
4. 一次只发送一个短动作；动作效果未知不得叠加下一次动作。
5. 单件失败或位置准备/证明失败不升级为整次失败；会话致命故障不因“还能重试”而继续。
6. 覆盖结论只由范围、连续覆盖、每格结局和末端证据推出；可信计数若存在则参与对账，但不是必要条件，也不由 OCR 成功数或“看起来走完了”推出。
7. 原始证据、每次尝试的判定和失败原因保留；不能用最后一次覆盖第一次。
