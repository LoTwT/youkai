# 扫描器重新架构决策（草案）

> 状态：**草案**（2026-10-28）。本文只记录重新架构的方向、已确认事实与当前决定，不修改任何现有规格正文。最终版需在“待核实事实”取得真机证据后由 PR-D2 定稿，并同步修改[架构](../specs/scanner-architecture.md)与 [T5](../specs/t5-zzz-inventory-traversal.md)。F1–F7 的证据是定稿前提；F8 的 Windows 证据按用户安排另行取得，未完成前 Windows 相关结论保持待验证。
>
> 范围：只讨论《绝区零》驱动盘仓库六位置遍历的感知、位置证明、完整性核验与故障恢复。字段识别、导出格式、UI 外壳与平台后端不在本文重写；它们按现有契约继续使用。
>
> 阅读标记：**[事实]** 直接读代码、日志或文档；**[评审]** 来自两份独立评审会话；**[控制者提供]** 任务摘要或消融实验结论；**[推断]** 设计判断，需实现或实机验收；**[待核实]** 需真机证据，见第 7 节。
>
> 2026-10-28 用户已回答先前的五个未决事项，结论并入 §4.6 与 §5；仅余重试预算一项未决（§10）。

## 结论摘要

- 保留 Go + MyGo、ONNX Runtime + PP-OCRv6 small、ScreenCaptureKit/Quartz、GDI/SendInput 的现有技术栈，也保留现有串行控制骨架。**不做一次性重写**，按阶段替换遍历证据模型。
- 目标形态：**同帧特征（含质量与来源）→ 连续位置验证 → 账本提交 → 完整性核验；失配时有界重新建立位置证明或回顶重走**。
- K1 把“按内容重定位”改成“重新建立位置证明”：账本主键是位置 + 绝对行 + 列 + 尝试；内容指纹只筛候选，候选唯一才继承已采集状态，否则回到已证明顶部重走；仍无法建立则把该位置标为不完整，继续后续位置，最终报部分（会话致命故障除外）。
- K2 用同帧、遮罩、归一化特征、最佳对次优竞争和多帧停稳模型替换单一绝对像素阈值；阈值按客户端 profile 标定，调参集与封存验收集按完整扫描划分。
- K3 的选中驱动推进（边缘点击/键盘）只在对应客户端实测通过后启用；任何动作都要闭环确认实际位移，动作未决不得换另一种输入补救。
- K4 完整覆盖由范围证明（S 选中态、其他筛选已清空、排序与方向）、到顶、每位置连续覆盖、每个占用格位有结局、到底证据推出；当前界面不显示数量，结果明确注明“本次未做计数对账”，不因缺少计数而降低覆盖。
- K5 把故障分为物品局部、可重试动作、可重建位置、会话致命四类；区分未投递、效果已确认、已投递效果未知，效果未知先重新观察或定位再决定动作。
- 三客户端（macOS 云、Windows 云、Windows 完整客户端）共享安全规则与账本，分离布局、遮罩、噪声范围、时序与导航能力；三个客户端分别验收，Windows 实测时间另行安排。
- 暂不做跨重启续扫；先做同一次扫描内的有界恢复，三客户端验收后再单独评审跨重启。

## 1. 背景与证据

### 1.1 直接失败：正确的 4 行位移被绝对阈值拒绝

2026-10-28 16:44 的 macOS 云客户端扫描在位置 1、视口 4（viewport_from=4）停止。诊断目录为 `~/Library/Logs/Youkai Dev/diagnostics/20261028-164452514-pos1-vp4-scroll-lost/`，逐帧证据见其 `manifest.json`。

**[事实]** 直接阻塞条件不是“没有正确位移证据”，而是“正确位移的误差略高于绝对上限”。同轮成功滚动的余量只有 0.10–0.29，说明 10.0 这个上限已经贴着真机分布的边缘；任何画质、编码、动画或选中效果的小变化都会把正确位移推到阈值之外。

**[评审]** 评审者 Kimi 对同一失败帧做了纯离线复核：正确 4 行对齐的归一化相关（NCC）约 0.952，其他整行候选约 0.78–0.80；33 个持续帧的正确对齐 NCC 为 0.941–0.966。这个结果说明归一化特征有潜力，**但同一组现场帧不能兼作新阈值的独立验收**。

见 [Kimi 评审会话](lody://session/ab09f5ca-0ffc-4cf8-b5af-ef08b9175a82?workspace=jh71jrcd7n3s48y9vbscr9p8w98dgyyz)。

**[控制者提供]** 2026-10-28 的消融实验结论是：安全逻辑（不猜、不去重、失败即停等）的测试覆盖较好；感知阈值此前没有被测试约束，已由 [#93](https://github.com/LoTwT/youkai/commit/e249db3) 补测试。

**[事实]** #93 的测试把“四行对齐误差 11 应拒绝”固定为期望（`internal/game/zzz/collect/scroll_thresholds_test.go` 的 `TestMatchScrollDisplacedErrorCapBoundary`），而真机失败帧的正确四行对齐恰好落在 10.90–13.11。这些测试锁住了现有边界，**不证明边界适合真机分布**。

**[事实]** 阈值和测试夹具同源：夹具来自 2026-10-19 的 M2 样本采集轮，`internal/game/zzz/collect/testdata/maccloud/README.md` 记录当前为 70 件掩码条目（60 `item` + 10 `scroll`）；任务摘要称“71 帧”，两者口径不同，本文按“同一次 2026-10-19 采样”表述，不把具体条数当作阈值依据。夹具 README 也明确：这些回归测试证明掩码没有改变判定，不替代真实客户端验收。

### 1.2 动作状态机缺陷：效果未知时再次拖动

**[事实]** `awaitScroll` 的终局汇总只有三条分支：已有 candidate 但未停稳、见过 `Lost`/ambiguous、见过 `Stationary`；没有显式的 `Undecided` 状态。`Undecided` 帧不会清除此前的 `sawStationary`/`sawLost`/`sawAmbiguous`，因此“先见过 Stationary、后又出现 Undecided”会在预算到期时汇总成旧的 `Stationary`；本次现场是同一缺陷的另一种表现：5090 先判 `Lost`，其后的 34 帧 `Undecided` 没有清除 `sawLost`，终局因此仍是 `lost`。

见 [inventory.go:2808](../../internal/game/zzz/collect/inventory.go#L2808) 的 `finish`、[inventory.go:2816](../../internal/game/zzz/collect/inventory.go#L2816) 的 `sawLost` 汇总与 [inventory.go:2948](../../internal/game/zzz/collect/inventory.go#L2948) 的判定 switch。日志的 `outcome=lost` 与 “no unique correspondence verified” 文案就是这个汇总路径的结果。

**[事实]** `scroll()` 在尝试循环外取 `before`（[inventory.go:2574](../../internal/game/zzz/collect/inventory.go#L2574)），重试时仍用同一个旧基准拖动并比较；每次 `awaitScroll` 又新建 trace（[inventory.go:2791](../../internal/game/zzz/collect/inventory.go#L2791)），`waitOut` 被覆盖，诊断只保留最后一次等待。见 [inventory.go:2604](../../internal/game/zzz/collect/inventory.go#L2604)。

**[事实]** `scroll()` 在 `out.stationary` 和默认的无明确终局分支都会再次拖动（[inventory.go:2692](../../internal/game/zzz/collect/inventory.go#L2692)、[inventory.go:2699](../../internal/game/zzz/collect/inventory.go#L2699)）。默认分支正是“没有可验证终局”，也就是动作效果未知；此时再发一次拖动，违反 T5 “首次动作效果尚不明确时，不发送验证用的下一次动作”的约束（[T5 §4](../specs/t5-zzz-inventory-traversal.md#4-一件物品何时可以进入识别队列)）。

**[事实]** 最新失败日志为 `attempts=2`、`drag_ms=2812`、`settle_ms=10023`，与“两次 5 秒等待”一致。第一次尝试的帧/判定仍未被保留；第二次尝试可见 5090 `Lost` 与随后 34 帧 `Undecided`（5096→5154 间有帧被保留策略丢弃，总计 `dropped_frames=8`，判定不可见），终局 `lost` 来自 5090 的 `sawLost` 未被清除，而不是 34 帧都没有判定。状态机允许在 `stationary` 和无明确终局分支再次拖动，且第二次仍用旧基准；两份评审都指出了这一限制。

**[推断]** 1.1 与 1.2 的叠加方式：1.1 的绝对阈值使 5096–5357 的正确 4 行位移全部落在 `Undecided`，无法形成 candidate；1.2 的粘滞状态使 5090 的 `Lost` 不被后续 `Undecided` 清除，`finish` 因此把终局标成 `lost`。只修 1.1，5096+ 会变成 `Displaced` 并可能停稳；只修 1.2，仍然没有可提交的 candidate，扫描仍不能完成。两者必须都修。

**[推断]** 这条缺陷把一次未决的滚动放大成两次拖动叠加、旧基准比较和首次证据丢失；不能只在 K5 上增加重试。

### 1.4 现有完整性与测试覆盖的缺口

**[事实]** 架构要求全部覆盖同时具备范围、起点、排序、连续遍历、末端证据和可用的同范围总数（[架构“完整性与身份”](../specs/scanner-architecture.md#完整性与身份)）。

**[事实]** T5 的实现口径写成了“若存在可信的同范围计数，与遍历账目一致”（[T5 §5](../specs/t5-zzz-inventory-traversal.md#5-滚动衔接重复物品与末尾)），因此当前可以在没有可信计数时仍声明 `complete`。在新决定下，这一行为不再是待修复的缺陷，而是与“当前界面不显示数量”相匹配的产品选择；需要改的是架构原文的计数要求。

**[用户确认 2026-10-28]** 当前游戏界面**不直接显示数量/容量**。因此本文不再把计数作为完整覆盖的必要条件：完整覆盖改为“范围已证明 + 到顶 + 每位置连续覆盖 + 每个占用格位有结局 + 到底证据”，结果中注明“本次未做计数对账”。这与架构 §5 原文“完整覆盖需可用的同范围总数”不同，属于**有意放宽**，列入 PR-D2 需同步的规格变更；将来若取得可信的同范围计数，再增加对账，混合稀有度的全仓总数不能冒充 S 级总数。

**[事实]** 当前 S 筛选只验证漏斗 `Active`，S 控件选中态没有像素探针；排序探针只验证“稀有度”标签，不读取升降序方向（[T5 §3](../specs/t5-zzz-inventory-traversal.md#3-开始前必须核对的页面条件)）。因此“范围成立”目前弱于“漏斗亮着”。

## 2. 选型复核

| 选型 | 结论 | 依据与代价 | 触发重新评估的条件 |
| --- | --- | --- | --- |
| Go + MyGo | **保留** | 当前失败没有指向 UI 框架、构建或分发；MyGo 已承担窗口、交互与打包。 | MyGo 的图片/长列表/输入法或分发在两平台实测中成为主要瓶颈，且无法在现有边界内解决。 |
| ONNX Runtime + PP-OCRv6 small | **保留** | 以 [ocrlayout.go:6](../../internal/ocrlayout/ocrlayout.go#L6) 常量为准：ORT 1.29.0、`PP-OCRv6_rec_small.onnx`。背景材料里的“PP-OCRv5”是旧称/参考实现说法，不是本仓库当前模型。千件级采集已证明 OCR 主路径可用。 | 独立验收集出现不可接受的自动接受错误或拒识率；原生推理崩溃、终止超时或持续泄漏；需要换模型/换后端才能满足三客户端质量门槛。 |
| ScreenCaptureKit + Quartz（macOS） | **保留** | 已有窗口流、几何与输入实测；本次失败是感知判定，不是采集失效。 | 受支持配置上持续黑屏、旧帧、帧时间不可用或成本过高；届时再比较其他 macOS 窗口采集路径。 |
| GDI + SendInput（Windows） | **暂时保留** | Windows 仍是计划内客户端，但遍历尚未实测；SendInput 受 UIPI 限制，输入成功不等于游戏响应。 | GDI 在正确裁剪下持续黑屏、返回旧帧或性能不足时，再评估 WGC；WGC 提供窗口帧和系统时间，但仍不能证明云端动作完成，且增加 WinRT/D3D 集成成本。 |
| 引入 gocv/OpenCV | **否决（暂不引入）** | 当前需要的是遮罩、降采样、归一化相关、梯度/边缘和候选竞争，Go 标准库与现有像素代码可以完成；引入 OpenCV 会增加 C++ 原生构建、签名、双平台分发与调试成本。 | 手写配准/检测代码明显变大且难以验证，或出现必须依赖成熟几何配准/检测算法才能跨客户端稳定的场景；届时按收益/成本重新评估，不是永久禁止。 |
| 检测/分类模型 | **暂不引入** | 可能改善格子、选中框、角标和滚动条提取；但需要三客户端标注与独立验证，且**不能给重复物品创造身份**，不能解决 K1 的实例歧义。 | 选中框、格位或滚动条在多个受支持画质下难以稳定提取，且小模型（可复用 ORT）的收益超过标注与验证成本。 |
| 外部数据途径 | **不采用** | Enka 的公开结构是展示角色装备（`EquippedList`），不是完整仓库，见 [Enka ZZZ API](https://github.com/EnkaNetwork/API-docs/blob/88fc20697fda924430943434c11e0c45eb39509f/docs/zzz/api.md#equipment)。抓包（如 [zzz_packet_capture](https://github.com/AleXu224/zzz_packet_capture)）需要登录流量、相应权限和随版本维护的成本，未证明适用于 macOS 云客户端；内存读取/注入在云客户端不可得，且带来兼容性、反作弊、安全和维护风险。 | 用户明确改变产品范围并接受新的授权/安全边界；在此之前不把外部数据当作扫描替代或身份来源。 |
| 录像/截图导入 | **仅开发与回放** | 有利于失败回放、回归和人工救援；不替代实时扫描，也不作为用户可用数据来源。 | 仅在开发/验收工具范围内扩展，不进入首版产品导出或自动扫描路径。 |

**[推断]** “保留技术栈”不等于“三个客户端都已验证”。Windows 的遍历、布局和输入仍是未完成证据；选型复核的结论是“当前没有证据要求更换”，不是“已经证明三客户端可用”。

## 3. 参考实现的可迁移机制

以下只记录可核对的行为；参考项目的成功不等于 youkai 三个客户端会得到同样结果。固定版本链接优先使用评审已核对的提交。

### 3.1 YAS `757689f0`

## 4. 决定：修正后的 K1–K5

### 4.1 总体形态

保留现有串行控制骨架：一个控制者按“选择 → 验证选择 → 等待就绪 → 采集”推进，平台与 OCR 仍按现有边界工作。替换的是遍历证据模型，不是一次性重写整个扫描器。

```text
同帧图像
  → 感知：格子/行签名、选中、详情指纹、滚动条、计数（若界面提供）
  → 连续位置验证：行重叠、选中锚点、滚动轨迹
  → 账本提交：位置 + 绝对行 + 列 + 尝试
  → 完整性核验：范围 + 顶部/连续/底部（计数可选）
        失配 ↙
  有界重新建立位置证明（唯一候选继承 / 回顶重走）
        失败 → 该位置标不完整，继续后续位置，最终报部分
```

设计原则：

1. **证据优先于速度。** 不因“看起来像同一件”而跳过格位，不用 OCR 成功数推断覆盖。
2. **动作闭环。** 每次输入后先观察实际效果，再决定下一个动作；效果未知不叠加动作。
3. **最小替换。** 先在现有 `Matcher` 和 `scroll()`/`awaitScroll` 接缝内改判定，再引入账本与恢复；每阶段合并后扫描仍可用。
4. **客户端分离。** 共享安全规则、账本和故障分类；布局、遮罩、噪声、时序和导航能力按客户端 profile 分离。
5. **保留原始证据。** 每次尝试的输入、帧、判定和失败原因都保留；不能用最后一次覆盖第一次。

### 4.2 K1：重新建立位置证明

**决定：** 不把“可重定位”定义为“通过物品内容找到它原来在哪一行”。改为：当连续位置验证失效时，重新建立**位置证明**；内容特征只用于缩小候选。

- **账本主键：** `位置 + 绝对行 + 列 + 尝试`。位置是转盘 1–6；绝对行从已证明的顶部起算；列是当前视口内的 0–3 列；`attempt` 区分本次会话内的遍历/恢复尝试，不是物品身份。
- **内容指纹：** 格子缩略图签名、行签名、详情指纹只用于筛候选。它们不能证明“两件盘相同”，不能跨格位合并、删除或跳过观测。
- **继承条件：** 当前可见内容在账本中只能对应**唯一**候选时，才允许继承该候选的已采集状态；继承只免除重复接纳，不免除当前帧的占用、位置连续性和范围核验。候选不唯一时，可用相邻行/滚动轨迹消歧；仍不唯一则回到已证明的顶部重走；重走仍无法建立位置证明时，把该位置标为不完整，继续后续位置，最终报部分。
- **禁止：** 不得按指纹匹配直接跳过格位，不得把两个观测合并成一件，不得用计数反推“缺的那一件在哪一行”。计数只能证明数量，不能提供位置身份。
- **重访：** 同一格位标记未解决后重访成功，新观测取代旧观测，结果只算一件；旧 attempt 作为“已被取代的尝试”保留在诊断记录，不计入任何件数（不进 `excludedCount`）。若旧观测在接纳前已经分配 `sequence`，这与 scan JSON v2 的计数等式冲突，实现路径见 §9.4。
- **重走：** 回顶重走必须重新证明顶部、范围、排序和方向；重走时继承已解决格位要逐行/逐格核验当前内容，不能只靠旧截图或旧绝对行。

**[推断]** 这条决定与“不去重、不猜”一致：内容特征可以帮助“找候选”，但不能单独承担“这就是同一件”的结论。真正相同的相邻盘仍各算一件；无法消歧时宁可把该位置标为不完整并继续后续位置，也不合并观测。

### 4.3 K2：感知

**决定：** 把“整视口灰度 MAD + 绝对阈值”升级为“同帧、遮罩、归一化特征、最佳对次优竞争、多帧停稳”的组合判定。

- **同帧：** 格子签名、选中框、详情、滚动条和计数（若界面提供）必须来自同一帧或明确绑定的帧 ID；不把不同时刻的特征拼成一次判定。
- **遮罩：** 动态选中框、鼠标悬停等变化区域遮掉；装备头像、管理状态角标等**可区分证据分通道保留**，不能为了降噪把所有角标都遮掉。遮罩范围按客户端 profile 标定。
- **归一化特征：** 使用归一化相关、梯度/边缘或等价的尺度无关特征；在可比的支持区域上比较。均匀图像、低信息量区域不能因为“最佳候选分数高”而接受。
- **最佳对次优竞争：** 不仅看最佳候选的绝对分数，还要求最佳与次优整行/整格候选有足够差距；差距不足时保持未决。
- **多帧停稳：** candidate 必须相对自身连续观测稳定，不能用“相对拖动前帧仍是同一行数”代替停稳；迟到惯性、云视频重复帧和底部回弹都要纳入停稳模型。
- **保留拒绝条件：** 信息量不足、重叠少于一整行、画面运动超出模型（窗口/几何/页面变化）时拒绝，不进入候选竞争。
- **阈值与验收：** 阈值按客户端 profile 标定；调参集与封存验收集按**完整扫描**划分，同一扫描的相邻帧不得跨组。现场失败序列可以进入调参集，但必须另采完整扫描做独立验收。

**[评审]** Kimi 的 NCC 复核只说明“正确对齐与错误候选在归一化特征上可分”，不构成阈值验收；Sol 也强调特征签名同样需要阈值，模糊画面也会产生最佳候选，不能只凭排名接受。

### 4.4 K3：推进方式

**决定：** 选中驱动（边缘点击、方向键、`d` 键等）是候选路径，不是默认路径；只有对应客户端实测通过后才启用。

- **动作闭环：** 任何动作（点击、拖拽、键盘）都要在动作后确认实际位移/选中变化；不能“点了就假定一行”。
- **动作未决：** 上一次动作效果未知时，不得切换另一种输入方式补救（例如点击未确认就改拖拽）；先重新观察或定位，仍无法确认则重建位置；仍失败则该位置不完整并继续后续位置（会话致命除外）。
- **每个客户端一条已验证路径：** 拖拽仍是基线；边缘点击/键盘推进按客户端分别验证（F2/F3/F5）。未验证的客户端保留拖拽或停止，不共享“某个客户端有效”的结论。
- **坐标事务：** 边缘点击可能带动列表；点击前的坐标和点击后的位置必须分开记账，旧坐标不能直接用于下一次点击。

### 4.5 K4：完整性

**决定：** 先证明范围，再核对覆盖与末端证据；计数不是完整性的必要条件。

完整覆盖的必要条件（缺一即 `partial`/`unknown`）：

1. **范围：** S 选中态有直接证据（不只是漏斗 `Active`）；其他筛选已清空；排序标签和**方向**已读取/验证。单次面板访问内完成并记录证据；无法证明就降级。
2. **顶部：** 稳定非移动的顶部确认；不能以“向上滚了很多次”代替。
3. **连续覆盖：** 每个位置的每次移动都有可解释的位置对应；不允许无法解释的跳跃。
4. **每个占用格位有结局：** 每个占用格位有 S 接纳、非 S 跳过或未解决结局；未解决不能消失或被静默跳过。
5. **底部：** 独立底部证据（最后一步不足整步、或 `Bottom + Stationary`）。
6. **重复物品：** 相邻且详情完全相同的 S 盘各算一件；参照往返只解决“详情是否属于当前目标”，不建立跨视口实例身份。

**覆盖与结果完整分开：** 所有位置都走完（范围、顶部、连续覆盖、每格结局、底部成立）时，`coverage` 仍可为 `complete`；未解决格位在可用结果/导出中如实标注，不能因为 `coverage: complete` 就把未解决件当作可用。

**计数（可选，不是必要条件）：** 用户于 2026-10-28 确认当前游戏界面不直接显示数量。结果中必须明确注明“本次未做计数对账”；若将来取得可信的同范围计数，再增加对账。混合稀有度的全仓总数不能冒充 S 级总数（T5 已有此规定）；计数只能证明数量，不能定位缺哪一件。

**[评审/用户确认]** Sol 指出旧套装筛选残留时“剩余列表全是 S、读数正确、走到底、采集数一致”仍可能漏扫；Kimi 指出计数只能证明数量，不能定位缺哪一件。用户随后确认当前界面不显示数量，因此本文把计数降为可选对账，而不是完整覆盖的门槛。

### 4.6 K5：故障分级

**决定：** 按故障影响面分级，而不是把所有失败都送进同一个重试/停止路径。

| 级别 | 例子 | 允许动作 | 结果与记账 |
| --- | --- | --- | --- |
| 物品局部 | 单件详情无法归属、单件 OCR/字段失败、单件证据缺失 | 标记未解决，继续当前位置；稍后自动重访；成功时新观测取代旧观测 | 结果只算一件；旧尝试作为“已被取代的尝试”保留在诊断记录，不计入任何件数（不进 `excludedCount`）；仍失败则可用结果标未解决，`coverage` 可仍为 `complete` |
| 可重试动作 | 点击未生效、拖拽无位移、选中框瞬时消失、动作迟到但可观察 | 只有明确“未产生效果且无迟到动作风险”时才有限重试；每次尝试独立记录 | 效果未知先重新观察/定位，不直接重发；不得换输入方式 |
| 可重建位置 | 滚动位置丢失、绝对行无法确认、列表仍同范围 | 有界自动重新建立位置证明：唯一候选继承，或回已证明顶部重走 | 预算耗尽仍无法建立→该位置标为不完整，继续后续位置，最终 `coverage=partial`；不猜行数 |
| 会话致命 | 失焦、窗口替换/`targetLost`、几何变化、权限撤回、`pageUnverified`（云断连）、采集流停止、存储/证据失败、运行库故障、用户取消 | 停止输入、收尾、保存已接纳结果 | 停止整次扫描；覆盖保持部分/无法确认；不自动续扫 |

> 覆盖与结果完整分开：范围、顶部、连续覆盖、每格结局、底部都成立时 `coverage` 可为 `complete`；未解决格位只在可用结果/导出中标出。位置级重建失败只让该位置不完整并继续后续位置；只有会话致命故障停止整次扫描。每次物品重访或位置重建的内容都记录在结果/诊断中，供用户查看。物品局部的旧尝试记录同样受 §9.4 的 v2 计数等式约束。

动作状态必须区分：

- **未投递：** 平台明确未发送；可以按动作预算决定是否重发。
- **效果已确认：** 位移/选中/详情证据成立；提交并继续。
- **已投递但效果未知：** 先重新观察或定位；在确认前不得发送下一个动作。这条直接对应 T5 §4，也是 1.2 缺陷的修复原则。

**[推断]** “只有无法重定位才停”不成立。失焦、窗口替换、权限、存储和用户取消即使理论上“还能再找位置”，也必须停止整次扫描；位置级重建失败则只把该位置标为不完整并继续后续位置。K5 的动作由故障类别决定：会话致命停止，位置级失败降级并继续，物品局部重访。

### 4.7 三客户端 profile

| 维度 | 共享 | 分离 |
| --- | --- | --- |
| 安全规则 | 不去重、不猜行数、动作闭环、证据优先、失败如实降级 | — |
| 账本 | 位置 + 绝对行 + 列 + 尝试；覆盖语义；每个观测一个结局 | — |

**[事实]** 当前状态：

### 4.8 安全不变量

以下不变量不因重新架构而放宽：

1. 不按属性、图像哈希或详情指纹去重；相邻同详情盘各算一件。
2. 不猜滚动行数；没有唯一对应就重建位置；仍失败则该位置不完整并继续后续位置（会话致命除外）。
3. 每个已接纳观测恰好一个结局；不重编号、不删除旧观测。
4. 一次只发送一个短动作；动作效果未知不得叠加下一次动作。
5. 单件失败不升级为整次失败；会话致命故障不因“还能重试”而继续。
6. 覆盖结论只由范围、连续覆盖、每格结局和末端证据推出；可信计数若存在则参与对账，但不是必要条件，也不由 OCR 成功数或“看起来走完了”推出。
7. 原始证据、每次尝试的判定和失败原因保留；不能用最后一次覆盖第一次。

## 7. 待核实事实及核实方法

以下步骤只点击、截图、观察，不改代码；每项都要记录客户端、显示配置、位置和当时筛选/排序。

### F1 是否存在任何显示数量/容量的界面及其范围

- **要回答：** 当前三个客户端是否有**任何界面**显示仓库数量/容量（不仅是仓库页；也可能是标题区、筛选面板、角色/装备页）？若有，表示全仓、筛选后结果、当前转盘位置，还是容量上限？能否稳定 OCR？用户 2026-10-28 称当前页面不直接显示，因此本项只作辅助核对候选，不是完整性的前提。
- **影响：** K4 的可选计数对账、阶段 3/6；不影响完整覆盖的必要条件。
- **核实步骤：** 逐个客户端查看仓库页、标题区、筛选面板、角色/装备页等可见界面，寻找数量/容量文本；若找到，连续截 5 帧并切换筛选/转盘观察变化。参考 ZZZ-Scanner.Next 的 `inventoryCount` 线索（见 §3.2）寻找类似标题区；没有则记录“无”。
- **判定标准：** 若存在且多帧读数一致、范围明确（尤其与 S 筛选范围一致），可作为未来对账候选；若不存在、不可读或混合范围，保持“本次未做计数对账”，不影响 `complete`。混合稀有度的全仓总数不能冒充 S 级总数。

### F2 云客户端点末行是否稳定只滚一行

- **要回答：** 点击当前可见末行（含首列/末列）是否只让列表滚一行？选中框是否跟随目标？是否有时多滚、少滚或不滚？
- **影响：** K3、阶段 4；也影响 K1 的绝对行推进。
- **核实步骤：** 在位置中部选一个可见末行格→截图→点击→等待稳定→截图；在不同视口、不同位置重复至少 5 次；分别测试末行首列、末列和短列表。观察位移行数、选中框和详情变化。
- **判定标准：** 列表精确移动一行（行距 147 帧像素）且选中框落在预期目标/下一行；重复稳定。若出现多滚、少滚、无响应或选中框跳变，则只能作为“需闭环测量的候选动作”，不能作位置证据；按客户端记录。

### F3 方向键/`d` 键能否移动选中、到边缘是否自滚

- **要回答：** 方向键或 `d` 键能否逐格移动选中？到视口边缘是否自动滚一行？是否触发其他 UI 行为？
- **影响：** K3、阶段 4、平台按键词汇。
- **核实步骤：** 打开仓库并选中一格→每次按一个方向键/`d`→每次截图；在首行、末行、首列、末列继续按键越过边缘；三个客户端分别重复。记录选中位置、列表位移和其他界面变化。
- **判定标准：** 每次按键精确移动一格/一行；边缘自动滚一行且选中框仍可跟踪；无其他动作。若按键无响应、跳格、触发面板或滚动多行，则该客户端不启用键盘推进。

### F4 S 选中态与其他筛选清空能否在单次面板访问内识别、排序方向

- **要回答：** 单次打开面板内，能否确认 S 芯片处于选中态、其他筛选已清空？排序标签和升降序方向能否读取？
- **影响：** K4、K2 遮罩、阶段 3；直接决定 `complete` 是否可能。
- **核实步骤：** 打开面板→截图；切换 S 开/关→各截图；逐项检查套装、槽位、等级、锁定、弃置、装备等筛选的显示状态；读取排序标签和方向指示；关闭面板→确认漏斗；每个位置/客户端至少做一次。
- **判定标准：** S 选中态有稳定、可区分的视觉证据（不能只看漏斗 `Active`）；其他筛选有“已清空”证据；排序标签与方向都能验证。任一项无法证明→范围不成立，只能 `partial`；方向不可读时不能把 `sort:"verified"` 当作方向证明。

### F5 滚动时选中框是否跟随同一件盘

- **要回答：** 拖拽、边缘点击或键盘推进时，选中框是否停留在同一件盘上并随列表移动？还是会跳到首行、消失或重置？
- **影响：** K1、K3；决定选中锚点能否用于位置证明。
- **核实步骤：** 选一件有辨识度的盘→截图→滚动一步/点击推进/按键→截图；重复多次，并加入相同缩略图的相邻盘。记录选中框相对物品的位置。
- **判定标准：** 选中框持续跟随同一件盘，或按可预测规则移动到相邻格；若跳变/消失/重置，则选中框不能作为跨滚动锚点，只能作当前帧的选中证据。

### F6 相同缩略图/相同详情的最长连续区间、是否存在整屏无可区分参照

- **要回答：** 同套装同缩略图、同详情、同管理状态的连续区间有多长？是否存在整个视口都找不到可区分参照的情况？
- **影响：** K1、K2、阶段 2/3；决定“唯一候选继承”是否经常可行。
- **核实步骤：** 用已知库存（或人工可控账号）逐位置、逐视口截图；遮掉动态选中框/悬停后离线比较格子签名和详情指纹；统计最长连续相同区间，并检查每个视口是否有至少一个可区分参照。
- **判定标准：** 记录每个客户端/位置的最长区间和“整屏无可区分参照”的出现频率。若整屏不可区分，唯一候选继承不成立，必须回顶重走；仍无法建立位置证明时，把该位置标为不完整并继续后续位置；不能按内容去重。

### F7 动作时序矩阵

- **要回答：** 点击、拖拽、边缘点击、键盘在无响应、迟到、惯性、底部回弹、断连恢复时分别表现如何？哪些动作可以安全重试？
- **影响：** K3、K5、阶段 1/4/5。
- **核实步骤：** 每个客户端、每种动作发送一次；在 0/100/300/500/1000/2000ms 截图；测试无效目标、迟到响应、释放后惯性、底部回弹、云断连后恢复；重复至少 3 次。记录“未投递/已确认/效果未知”。
- **判定标准：** 建立动作时序矩阵；只有“明确未生效且无迟到风险”的动作才允许重试；效果未知必须先观察/定位。矩阵未覆盖的动作不得进入自动恢复。

### F8 Windows 两种客户端的布局、截屏与输入

- **要回答：** Windows 云客户端与完整客户端的布局、GDI 画面、SendInput/UIPI 行为、计数/筛选/排序/选中/边缘行为是否与 macOS 云一致？是否存在黑屏、旧帧或输入不响应？
- **影响：** 三客户端 profile、K2/K3/K4、阶段 4/6。
- **核实步骤：** **等后续安排**。届时在 Windows 云与完整客户端分别重复 F1–F7；核对 GDI 裁剪、帧时间、输入权限和窗口身份；未支持配置必须能拒绝。
- **判定标准：** 两种 Windows 客户端分别通过；任一端的成功不能替代另一端；未取得证据前 Windows 相关能力保持“未验证”，不宣称首发通过。

### 8.2 Sol 评审

会话：[lody://session/c0d3c7c0-9039-461a-b090-7d2fd2574ac1](lody://session/c0d3c7c0-9039-461a-b090-7d2fd2574ac1?workspace=jh71jrcd7n3s48y9vbscr9p8w98dgyyz)。总体立场：**有条件支持**，建议“连续定位为主、有界重定位恢复、独立完整性核验”。

主要意见：

1. **高 K1：** 重定位必须允许多个候选；详情指纹无法保证实例位置；指纹只筛候选，唯一才继承；否则回顶重走或停止部分；按指纹跳过会与“不去重、不猜”冲突。
2. **高 K4：** 范围验证优先于计数；旧套装筛选残留时，数量、走到底、采集数一致仍可能漏扫；完整性要同时有范围、顶部、连续、每格结局、底部和可信计数。（用户随后确认当前界面不直接显示数量，本文据此把计数降为可选对账，见 §4.5/§5。）
3. **高 K5：** “步骤重试”需要动作语义约束，不能统一兜底；区分未投递、效果已确认、已投递效果未知；效果未知先观察/定位；失焦、窗口替换、权限、存储、用户取消仍须终止。
4. **高 K5：** 检查点续扫与“记录/导出/UI 不动”不能同时无条件承诺；先做会话内恢复；跨进程续扫需额外的位置账目、范围代次、未决动作和锚点证据。
5. **中 K2：** 直接根因正确，但“视频流不能做绝对像素比较”过宽；云编码、背景、动画、选中效果各贡献多少误差未分解；特征签名同样需要阈值和质量检查。
6. **中 K3：** 选中驱动值得优先验证，但优先级由客户端证据决定；选中框可作为独立锚点；边缘点击要分别证明目标选择、位移和停稳。
7. **中 双端：** 实际是三个客户端 profile；Windows 遍历仍接 Mac 布局/标定，按键表无方向键；平台层应保留后端与安全契约，但允许必要扩展。
8. **中 开发流程：** 更深层问题是证据分布与验收顺序；现有夹具集中来自 10 月 19 日，#93 只固定边界，不证明规则适合新分布；按完整会话划分调参与封存。
9. **参考实现补充：** ZZZ-Scanner.Next 的移开鼠标复核、所有特征绑定同一帧；HSR-Scanner 的点首格后用 `d` 键；YAS 的云端单独等待路径；Inventory Kamera 的底部反向补扫与多尺度 OCR 投票。
