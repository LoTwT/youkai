# T3：OCR 运行库、模型与样本评估

更新日期：2026-10-16。状态：首轮验证组合已固定并完成制品静态核查；尚未安装依赖、加载运行库或运行识别。用户已认可模型评估方向与准确性边界：v6 small 优先验证，保留未知与人工校对，不承诺自动识别 100% 正确。字段范围由[架构第 6 节](scanner-architecture.md#首版字段清单提案)维护，模块边界、取消与分发要求以[架构第 4 节](scanner-architecture.md#4-ocr原生资源与构建)为准。

## 1. 当前建议

优先评估本地 CPU ONNX 推理：由游戏适配器定位详情中的字段区域，识别器完成预处理、推理和解码，再由适配器解释字段。固定区域能否可靠定位由 T5 验证；区域未知或页面不符时停止，不把整张截图直接交给文字识别模型猜布局。

根据公开评测，优先验证 PP-OCRv6 small，以 tiny 比较更小体积的代价，保留 PP-OCRv5 作为参考路线基准。最终根据三组真实样本选择一个随包模型，不默认同时部署多模型。参考仓库采用的 v5 具体变体、文件摘要与字典尚未核实，不能将其直接称作 mobile 或 server 模型。轻量应比较安装体积、冷启动、进程总内存、识别耗时和人工校对量，不能只看模型大小。

首版建议一个识别工作者和小型有界队列，运行库随安装包提供。首轮固定 yalue v1.36.0、ORT 1.29.0 CPU 路径和 RapidOCR 发布的 PP-OCRv6 small ONNX 制品，Microsoft 官方 Go 包保留为替代；版本、制品和替换条件由本文维护。选择依据是两平台制品中的实际加载、字段输出、取消和重复运行表现，不以包名或标签有无代替验收。

### 技术组合分别负责什么

```text
T2 提供截图
  -> T5 确认详情属于当前物品，并定位字段区域
  -> 预处理：裁剪、颜色转换、缩放与补边
  -> Go 绑定通过 cgo 调用 ONNX Runtime
  -> 运行模型，按配套字符表解码文本
  -> T5 解析类型、数值和单位，输出结果或待校对原因
  -> T4 记账、保存证据，MyGo 显示和校对
```

| 组成 | 作用 | 首版评估重点 |
| --- | --- | --- |
| 识别模型 | 已训练好的图像到文字模型，ONNX 是候选分发格式。 | 中文套装与词条、数字、小数点和百分号能否正确识别；初期使用现有模型，不先训练专用模型。 |
| ONNX Runtime | 执行模型计算的原生推理引擎。 | Windows x64 与 macOS arm64 的 CPU 制品、实际依赖、模型算子、线程、取消与资源释放。 |
| Go 绑定与 cgo | 将 Go 中的张量、参数与调用传递给原生引擎。 | 不改变模型所学内容，但影响 API 覆盖、对象拥有权、错误处理、取消和构建。 |
| 字符表与解码 | 将模型输出索引还原成文字。 | 与模型输出类别和顺序严格配套；不能用套装名称清单替换。 |
| 游戏资料与解析规则 | 将文字解释为套装、槽位、等级、属性和数值。 | 资料版本、别名与单位；首版不按等级核对数值（见[架构字段校验](scanner-architecture.md#字段校验范围与资料来源)），数值正确性由本节门槛与人工校对保证。 |

**模型选择建议：**优先验证 v6 small 的依据见下方公开评测。tiny 只有在驱动盘样本上通过相同质量门槛才替换它；small 未通过质量门槛时再比较 medium，不能仅因 medium 通用分数高就增加首版体积。模型与绑定是两项选择；采用 v6 不意味着向用户分发 Paddle/Python 环境，也不证明目前候选 ORT 组合已支持该制品。

**绑定选择建议：**首轮采用 yalue v1.36.0 与 ORT 1.29.0，先缩小版本配套变量；它需要把会话取消接到 `RunOptions.Terminate`。Microsoft 官方 Go 包的固定源码已把 `Run(ctx)` 的取消接入原生终止，更接近 Go 调用习惯；如果其固定版本和双平台制品通过相同验收，可优先采用。两者都需要 cgo 和随包原生库，都不能保证原生调用在硬期限内结束，也都尚未在 youkai 运行。[yalue 版本说明](https://github.com/yalue/onnxruntime_go/blob/1f0fb0647fc7091b57ec72dcf0f666d2234e4d04/README.md) · [官方取消实现](https://github.com/microsoft/onnxruntime/blob/402979ac1bef89dcd55add41eaa7277c407599eb/go/onnxruntime/session.go)

**开发与用户安装：**开发机需要 Go 和对应 C 工具链，正式制品分别构建；用户安装时不需要 Go、C 编译器或 Python。Windows 随包提供匹配的 DLL 和应用本地的 VC++ 运行库；Mac 随包提供 arm64 dylib，核对依赖、最低系统与签名。模型转换若需要 Python，属于开发阶段工具，不因此把 Python 加入用户安装包。资源通过明确路径加载，不能依赖当前目录或恰好安装在系统中的另一版本。[ORT 安装要求](https://onnxruntime.ai/docs/install/)

**CPU 与停止：**先限制识别工作者及 ORT 内部线程，测量与游戏同时运行的负载。ORT 会在算子内部使用线程，只有一个 Go 工作者不代表只用一个 CPU 线程；官方还说明线程空转可能提高 CPU 和功耗。具体线程数由实测确定。取消先阻止后续游戏输入，再通知在途推理结束并等待释放，界面保持响应；不能通过直接丢弃 goroutine 或销毁模型假装停止。[ORT 线程说明](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)

### 效率判断与边界

目前结构适合作为首版起点，但没有性能测量，不能称为已证实最优。固定字段区域省去通用文字检测，模型会话复用避免逐件加载，串行输入与有界识别队列允许采集和识别重叠。优先做这些减少重复工作的措施，再测量瓶颈。

优先从同一张已确认归属的物品截图提取文字、锁定、弃置和装备的可见证据，能否全部可见仍待样本确认。有限图标优先评估模板或特征匹配；有代理人名称时读取文字，只有头像时比较头像素材、变体及云视频退化下的可区分程度。头像不清晰、素材未收录或候选接近时保留未知。若必须额外悬停或切页，需由 T5 评估导航成本，不能把它当作免费的 OCR 字段，也不能交给识别工作者自行操作游戏。

参考扫描器的固定源码已有像素读取复用及按文字宽度分桶的小批推理，可作为减少重复复制与补边计算的依据；并非本项目测得的加速结果。[参考识别实现](https://github.com/ZztIsolation/ZZZ-Scanner.Next/blob/ff90891140016d3f1b738d73cb6cd9b291e17cec/Ocr/PaddleOcrRecognizer.cs) 本项目可先比较一件物品内多行的小批推理，前提是实际模型支持对应动态维度；不为凑批长时间等待，也不增加无界队列。

疑难字段可以有限次重做预处理或推理；需要重新截图时，控制者必须证明当前仍选中同一件物品，否则保存待校对状态。不能在识别队列滞后时读取已经切换到下一件的画面。两次识别一致只能增加支持证据，不能证明结果必定正确。性能记录应分开测截图、等待游戏响应、裁剪、推理和保存；只有推理成为瓶颈才增加相关复杂度。

**实际原生文件与打包成本：**

- Windows 的 `onnxruntime.dll` 为 x64，16,149,344 字节；导入表包含 `MSVCP140.dll`、`MSVCP140_1.dll`、`VCRUNTIME140.dll`、`VCRUNTIME140_1.dll` 和系统 UCRT/API set。包中另有 21,856 字节的 `onnxruntime_providers_shared.dll`，首轮可一并保留；它不出现在主 DLL 的静态导入表，是否由选定路径动态加载仍待验证。PE 的 OS/subsystem 版本字段是 6.0，不能据此声称支持 Vista，导入 API、Go 和应用自身要求仍独立成立。
- Mac 选用 `libonnxruntime.1.29.0.dylib`，为 arm64，43,184,400 字节，`LC_BUILD_VERSION` 的最低系统为 14.0。已见加载项均指向系统 framework 或系统库，包含 CoreML/Metal；即使只使用 CPU，也不能当作不存在这些动态依赖。该文件摘要为 `68f6e54e695583adc371aef610ec4abb1ffaa3df656582922de7690f7e2000eb`；用绝对路径加载版本化文件，不依赖工作目录中的别名。

这使“轻量”有了初始体积依据。首轮先使用上游制品；只有实际安装体积、内存或速度未达目标，才比较 tiny/v4、精简 ORT 或其他提供器。自行裁剪运行库会增加算子覆盖、平台构建与升级成本，不能仅因压缩包带有调试符号就先维护自编译 ORT。

### 绑定与运行库的实际交接

yalue 的固定源码已提供内部线程配置、session config 和动态张量会话，可用于该模型的动态宽度。首轮由识别实现持有进程级 ORT 环境并复用模型会话，每次推理使用独立的 RunOptions；取消监听退出并与推理调用完成同步后，再释放 RunOptions 和张量。该库的 terminate 标志会保留，复用前必须清除；初版用每次独立的选项对象减少取消污染下一次推理的风险。[线程与取消源码](https://github.com/yalue/onnxruntime_go/blob/1f0fb0647fc7091b57ec72dcf0f666d2234e4d04/onnxruntime_go.go)

Microsoft Go 固定提交 `402979ac1bef89dcd55add41eaa7277c407599eb` 仍是替代候选。其 [C shim](https://github.com/microsoft/onnxruntime/blob/402979ac1bef89dcd55add41eaa7277c407599eb/go/onnxruntime/cshim.c)从 API 27 逐级协商到 17，不能因源码来自 ORT v1.31.0 就断言必须换成 1.31 原生库。替代评估可先用同一个 1.29.0 制品、模型和样本检查协商结果及功能，控制比较变量；其 `Run(ctx)` 已有取消监听与返回前收尾。若它在相同验收中更可靠或明显减少胶水代码，可替换 yalue，首版不同时分发两种绑定。

Windows 开发端的 MinGW cgo 工具链和运行端的 MSVC Runtime 是两项要求。显式加载主 DLL 不会自动解决它所依赖 DLL 的搜索；最终还需检查 youkai EXE 由 C 工具链带入的依赖。[Microsoft 运行库要求](https://learn.microsoft.com/en-us/cpp/windows/latest-supported-vc-redist?view=msvc-170) · [分发条件](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files?view=msvc-170)

**VC++ 运行库采用应用本地部署（用户 2026-10-16 确认）：** 所需的 4 个 x64 文件 `MSVCP140.dll`、`MSVCP140_1.dll`、`VCRUNTIME140.dll`、`VCRUNTIME140_1.dll` 取自 GitHub Actions Windows runner 上 Visual Studio 的 `VC\Redist\MSVC\…\x64\Microsoft.VC143.CRT` 目录（具体路径在打包 PR 实测确认），不从 vc_redist 安装器解包，随应用放在 EXE 所在目录，不运行需要提权的 VC++ 安装器，与 MyGo 的每用户安装（[NSIS 脚本](https://github.com/egoist/mygo/blob/4d8673cd2658a2c6e86b26c44751e57bf8174f91/cmd/mygo/nsis.go)）一致。代价是这些文件的安全更新由 youkai 发新版负责。版本不早于构建 ORT 1.29.0 所用的工具集，并在 M1 确认再分发条件、实际被加载的是随包副本，以及在没有安装过 VC++ 的干净 Windows 上能正常加载。

MyGo、yalue 和 ORT 的所读源码许可为 MIT，ORT 制品另带 `ThirdPartyNotices.txt`；RapidOCR 仓库和所读 [ModelScope v3.10.0 模型卡](https://www.modelscope.cn/models/RapidAI/RapidOCR/resolve/v3.10.0/README.md)声明 Apache 2.0。模型托管根目录的独立 `LICENSE` 未取得，因此交付前仍需将模型原始来源、转换说明和适用声明一起核对归档；不把一个仓库的许可当作所有第三方字体或可选文件的统一许可。首版无需携带 RapidOCR 的 Python 环境或可视化字体。

| PP-OCRv4 mobile | 10.5 MB | 83.23% | 未报告 |

该评测列出 macOS 和软件版本，但未交代 CPU 型号与线程条件；示例还把空识别结果的耗时记为零。因此耗时仅作为筛选线索，不能直接预测用户 M1 Pro 或 Windows 游戏并行负载。正文另有检测数据集数量说明，不能当成文字行评测的样本量。

PaddleOCR 自有评测的“屏幕文字”类别中，v6 small 为 79.7%，v5 mobile 为 57.6%；这是另一测试集，只能单独比较。它支持优先试 small 的判断，但不是独立第三方复现。该报告的整页管线测试中，M4 的 ONNX small 耗时仍高于 v5 mobile，说明“新版在所有平台都更快”不成立。[官方同组模型报告](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/docs/version3.x/algorithm/PP-OCRv6/PP-OCRv6.en.md)

由此建议 small 优先、tiny 作为更小体积的候选、v5 作为已有路线对照，medium 留作精度不足时的候选。v4 mobile 在这一文字行测试中也接近 small，体积更小，值得在缩减体积时一并比较；缺失的同组耗时不能从另一评测补入。不能把不同年份、数据集、A100 加速结果和 CPU 裁剪识别拼成一个排名；最终比较必须固定三组驱动盘样本、预处理、字符表、运行库、线程与硬件，不因列出候选就同时维护多套生产资源。

RapidOCR 已发布 v6 识别模型的 ONNX 与配套信息，无需从零转换；其清单区分 tiny 与 small/medium 的字符表。不能复用不配套的 v5 字典，也不能把公开评测记为这个固定文件在 youkai 的成绩。[固定资源清单](https://github.com/RapidAI/RapidOCR/blob/7cfd3d9ef786a2e538ca30df700325e72e85b5f5/python/rapidocr/default_models.yaml)

## 3. 模型配套资料

正式选定模型前，建议将以下信息作为一份版本化识别资源记录维护；模型、字典或预处理改变后重新验收，不分别追随各自的最新版本。OCR 字符表属于模型配套资源；游戏套装、属性词表属于适配资料，后者才可能从 fairy 的固定公开制品生成，二者不能混为同一份字典。

- 模型来源、具体变体、许可、文件摘要；若经过转换，记录原模型、转换工具版本、命令和导出配置。
- ONNX 输入与输出名称、数据类型、形状及动态维度，模型所需算子与运行库支持情况。
- 颜色顺序、归一化、目标高度、宽度上限、缩放与补边方式，以及文字区域的裁剪依据。
- 字典文件及顺序、空格处理、CTC blank 和重复字符折叠规则。若候选模型使用其他输出或解码方式，不能沿用旧 CTC 假设。
- 字段原文、识别分数及规范化结果之间的关系。模型分数不作为“字段正确概率”；游戏词表和数值规则可触发待校对，不能静默把近似文本变成确定答案。

最容易出现的集成错误是“运行成功且结果看似合法”，但模型与字典、颜色通道或补边规则不配套。应先检查固定裁剪图的预处理与解码，再比较整件识别质量。

### 固定 small 制品的输入与解码

以下模型信息来自对固定 ONNX 的静态解析；预处理和解码规则来自 RapidOCR 同一提交的[识别流程](https://github.com/RapidAI/RapidOCR/blob/7cfd3d9ef786a2e538ca30df700325e72e85b5f5/python/rapidocr/ch_ppocr_rec/main.py)、[图片加载](https://github.com/RapidAI/RapidOCR/blob/7cfd3d9ef786a2e538ca30df700325e72e85b5f5/python/rapidocr/utils/load_image.py)、[CTC 解码](https://github.com/RapidAI/RapidOCR/blob/7cfd3d9ef786a2e538ca30df700325e72e85b5f5/python/rapidocr/ch_ppocr_rec/utils.py)与配置。这里是 Go 实现应对齐的基准，未运行上游 Python。

| 项目 | 已读事实与集成要求 |
| --- | --- |
| 模型格式 | IR 10，默认域 opset 11；顶层图的节点均为默认域，未见外置 initializer 权重。仍需 ORT 实际建会话验证算子和图优化，元数据可读不代表可执行。 |
| 输入 | `x`，float32，`[N, 3, 48, W]`；N、W 为动态维度。允许动态维度不代表所有宽度、批量都已验证。 |
| 输出 | `fetch_name_0`，float32，`[N, T, 18710]`，T 为动态维度。按实际输出形状分配和释放，不用一个固定宽度预估所有输出长度。 |
| 颜色与缩放 | 上游识别使用 BGR；高度 48，按宽高比向上取整宽度并用线性插值缩放。其默认基准宽度为 320，按批次最大宽高比扩宽；先复现这一规则，再凭样本评估更窄输入。T2 的 BGRA/RGBA、stride 和方向必须先明确转换，不能直接当作三通道连续像素。 |
| 归一化与补边 | 转为 float32/CHW，按 `(像素 / 255 - 0.5) / 0.5` 归一化；右侧用归一化后的 0 补边。这与先补黑色像素再归一化不同。Go 插值与浮点结果需用固定裁剪样本对齐参考。 |
| 字符顺序 | `character` 元数据原文 UTF-8 为 74,946 字节，其 SHA-256 为 `f7aa897ca828a4c7c9e2739c30f9161a33306d532f020bcdb91dcfb664a5507e`。按行读取 18,708 项，不重排；索引 0 加 blank，末尾加空格。加载时校验最终表长等于输出类别数。 |
| 解码与分数 | 每个时间步取最高类别，先按相邻原始索引去重再排除 blank，保留被 blank 分开的重复字符。上游对有效字符分数求平均；这个分数不是字段正确概率，阈值仍由独立样本验证。 |

模型自带多语言字符不扩大首版游戏识别范围，页面与字段解析仍只支持已确认的简体中文。字符表随 ONNX 一起分发，可在资源记录中保存其独立摘要；游戏词表保持单独版本。一次推理只保留需要的文本、分数与证据，完整输出张量及时释放，不将所有时间步的类别分数长期存入扫描记录。

## 4. 三组样本与验收

验收目的是证明真实游戏图片能变成可信、可校对的 S 级驱动盘记录。初期不训练模型，标注样本用于选模型、调整预处理和检查结果。流程与数量为建议，尚未开始采样。

### 收集、标注与划分

1. 每种客户端先取约 20 至 30 件典型 S 级驱动盘，核对详情布局、可见管理状态、字体和云视频区域；这些已用于观察与调整的图片归调参集。一个样本保留一张可判断物品上下文的详情截图和对应字段裁剪，不仅保存压缩后的单个数字。
2. 随后每种客户端补足至少 200 件独立物品的场景样本，建议 100 件调参、100 件封存验收，三组至少 600 条场景样本。它们可包含同一批实际物品在不同客户端的画面，不代表必须拥有 600 件不同物品。数字是起点，缺少关键类型时继续补齐，不能用相邻视频帧凑数量。
3. 按[已确认的实体与语言范围](scanner-architecture.md#6-首版功能范围)收集简体中文样本，覆盖六个槽位、固定资料版本全部套装、0 至 15 级、全部合法主词条类型和十种副词条，兼顾不同行数、强化阶段、易混淆数字、小数点和百分号。锁定已是必需字段，分别覆盖锁定、未锁定及不可判读的图标；核实弃置与锁定是否共用区域，补弃置和无标记状态。装备识别补未装备、不同代理人、可见变体及无法分辨的例子。无需穷举全部字段组合，但每组必须记录覆盖表与缺口；不能用仅满级或仅未装备样本代替完整范围。
4. 为每件样本独立填写正确字段，保留原文与规范化值，关键数值或歧义由人工复核。不能将待测 OCR 输出直接当作标准答案。图片肉眼不可判读、缺字段、页面过渡和不支持的布局另外分组。
5. 同一实际物品在不同客户端、相邻帧以及缩放或压缩变体放在同一数据划分中。验收集不参与阈值选择；用它修复问题后，需要新保留样本检验修改，不能继续称旧集为未见验收集。合成退化图片不能代替真实云视频。

在 M2 采样前建立物品来源、跨客户端对应关系和划分清单，用人工样本编号表达，不假装扫描器可读游戏实例 ID。完整库存序列若用于布局、OCR、导航调参或排障，其可见物品也归开发侧，不能只换一次扫描会话就作为未见 OCR 验收物品。优先用隔离的开发物品范围或测试库存取得调参序列；这属于受控采样，不改变产品扫描全部 S 级的范围。无法隔离时，在调整结束后补取未参与开发的物品或独立库存；没有可用独立样本就如实标记缺口，不放宽已有门槛。OCR 以物品来源分组，导航同时以完整序列分组；正式封存集仅在候选构建和参数冻结后打开。

场景记录至少包含游戏版本、语言、客户端、显示设置、窗口点尺寸与图像像素、云视频区域、布局版本和可获得的画质信息。Mac 几何未知时先测量，不从屏幕型号推定视频分辨率。三组语料分别对应各客户端实际选定的首版显示配置，选择流程见 [T2 第 3.2 节](t2-platform-capture-input.md#32-可验收的窄显示配置候选)；切换候选或后续新增内置尺寸后，补齐该配置的真实样本与验收，不能只将旧图片缩放后当作已验证。其他语言及不支持配置作为拒绝或待处理案例，不计入支持范围内的成功样本。保留样本元数据与预期字段即可，暂不需要建设标注服务或训练平台。

三组分别覆盖可避免一组样本过少被总平均值掩盖；600 条只是起点，不是充分覆盖的保证。

### 指标与判定

| 指标 | 计算或候选要求 |
| --- | --- |
| 字段准确率 | 按套装、槽位、等级、词条类型及数值分别计数；未知、漏行与误增行不能算正确。锁定单列；弃置和装备者在纳入后同样逐状态、逐代理人检查，不能用多数未装备或无标记样本掩盖少数状态错误。 |
| 整件字段全对率 | 一件物品的全部必需字段正确才计为正确，分母为该组可判读且处于声明支持范围的样本；不能用大量正确文字掩盖一个数值错误。 |
| 自动接受错误 | 被程序标为可直接使用，却至少有一个必需字段错误的件数；各组保留验收集目标为 0 个已知错误。有限样本不保证上线后零错误。 |
| 自动正确完成比例 | 各组可判读支持样本中，至少 95% 自动接受且全部必需字段正确；待校对、拒识或失败合计不超过 5%。候选门槛在查看验收结果前确定。 |
| 负例处理 | 不可判读图片、非 S 级、缺失详情、错误页面或不支持布局分别验证拒绝、待校对或停止行为。负例单列，不混入正常样本的 5% 指标，也不能自动生成可信结果；同时报告原始收集总数、正常分母、各负例数量及不可判读占比，不让困难样本从报告中消失。 |
| 性能与资源 | 记录预处理、推理、解析和整件耗时，区分冷启动与热运行，报告 p50/p95、进程总内存及与游戏并行时的 CPU；限制阈值待基线实测后另定。 |

例如某场景有 100 件可判读验收样本，95 件自动通过且字段全对，5 件进入校对，可达到候选质量门槛；若其中一件把数值读错仍自动通过，则不通过。只报告字符准确率或模型分数不能替代上述指标。

### 能否承诺 100% 正确

不能承诺今后所有画面、所有库存的自动识别永远 100% 正确。固定、经人工复核的验收集可以要求观测到零个自动接受错误；这只描述已测样本。人工校对能够修复具体记录，但人工标注本身也可能有错，不能把“已人工检查”改写成数学保证。

错误还可能来自物品选择、旧帧、裁剪和遗漏，不只来自文字模型。合法数值校验不能发现所有“读错后仍合法”的结果；高分、两个模型一致或相邻帧一致也不能排除共同错误。系统应保留原图、原始输出和修订证据，将疑难项交给用户，不能声称所有错误都能被自动发现。

本节的 95% 候选门槛表示自动正确完成比例，其余进入校对或失败处理；不是允许 5% 错误静默混入结果。锁定未知，或所固定 [JSON 字段策略](scan-json-format.md#3-一件驱动盘)要求的装备、代理人或弃置状态未知，均不能计为整件自动完整成功；比较模型时必须使用同一策略，不能降级字段要求来提高成绩。识别质量和扫描覆盖分别报告，人工修正若干字段不能证明库存没有漏扫。

每场景 100 件保留样本只是初始比较。作为样本量的说明：若错误事件独立同分布，n 次观测零错误时，单侧 95% 二项上限为 1−0.05^(1/n)；n=100 约为 2.95%，n=3000 约为 0.10%。这些是条件假设下的统计上限，并非本项目错误率。真实样本往往同源且相关，需覆盖版本和场景后再讨论扩大验收；不能用重复帧或有限样本零错误证明普遍 100%。目前不把 3000 件设为已批准的采样任务。

### 验证阶段与分工

| 阶段 | 应取得的证据 |
| --- | --- |
| 不运行游戏的资料与制品核对 | 已完成摘要、原生依赖、Mac 系统标记、模型形状与字符表核查；VC++ 随包文件版本、最终资源声明及构建后依赖待补齐。 |
| 固定图片验证 | 两平台分别加载随包资源，检查错误架构、缺库、损坏模型、中文与空格路径、不同工作目录、取消和重复运行；对保留样本逐字段比对。 |
| 三种真实客户端验证 | 分组报告整件字段全对率、自动接受错误数、拒识率及人工校对量；区分截图选错物品、布局裁剪错误与 OCR 识别错误，不用 OCR 分数替代导航证据。 |
| 安装与负载验证 | 干净用户环境中断网用固定图片识别、校对和导出；实际扫描时记录 CPU、进程总内存、每件耗时和队列压力，另测冷启动与模型加载。云游戏本身仍联网。 |

图片验收之外，T5/T7 还需在三种真实客户端分别扫描完整的目标库存，对照人工基准核对逐件字段、数量、同属性重复物品和末页，并覆盖取消后部分结果。总数相同不证明没有漏一件又重复另一件；错误物品的清晰截图可能被 OCR 完全识别正确，所以还需详情归属和遍历证据。带操作与时间顺序的资料、整段序列划分和负例要求见 [T5 验收](t5-zzz-inventory-traversal.md#6-保存什么证据怎样验收)，不能仅靠本节的独立图片通过导航验收。

每批整仓对照使用有版本的独立人工基准，记录对应库存、字段、重复物品出现次数、筛选与排序；扫描输出不能自行生成自己的遗漏基准。该批扫描期间不强化、装备、弃置或增减物品；变化后重建基准，不能沿用旧数目。不同批次或客户端可以使用不同基准，只要逐批可追溯，不要求九次扫描共享一个永久不变的账户库存。

用户后续主要参与真实客户端与设备可用性、采样场景和有歧义标注的确认；无需先选 Go 库，也无需手工制作模型训练集。开发侧负责样本编号、裁剪、辅助标注、资源版本、差异报告和自动对比。需要的交付物为样本及覆盖清单、经复核的正确字段、固定资源记录、三组结果报告和失败证据。

取消与原生释放遵循公共会话契约：关闭游戏输入许可和原生推理返回分别记账。一次 Go 调用返回取消错误，不足以证明底层资源已结束，也不能提前销毁仍在使用的张量和模型会话。

## 5. 会改变建议的证据

若固定区域在支持的显示配置中无法稳定覆盖文字，先调整布局定位；确实需要检测时再加入文字检测模型。若小模型在三组保留样本中达到同样的质量门槛且显著减少实际成本，可替换基准模型。若两个绑定中只有一个能满足两平台加载、取消和反复使用要求，优先采用通过者。

只有在正确裁剪和受控线程下仍证实 CPU 推理是瓶颈，才评估加速；可复现的原生崩溃或无法接受的停止行为才触发辅助进程方案。
